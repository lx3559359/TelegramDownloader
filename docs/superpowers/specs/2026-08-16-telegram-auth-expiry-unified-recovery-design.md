# Telegram 授权失效统一恢复设计

## 背景

v0.11.0 的自动订阅调度器会把 `SessionExpiredError` 转换为规则状态
`auth_required`，但不会通知应用的全局会话失效流程。与此同时，
`ensure_telegram_online()` 在传输连接仍存在时只检查 socket 状态，不验证账号授权，
因此界面可能同时显示“连接正常”和“需要重新登录”。现有错误记录还会丢失
Telethon 授权异常的具体类别，只留下笼统的 `SessionExpiredError`。

## 目标

- 后台订阅发现授权失效时，立即进入与前台操作相同的重新登录流程。
- 只有传输连接和账号授权都有效时，界面才显示“连接正常”。
- 日志与健康诊断报告记录固定、脱敏的授权失败原因码。
- 界面继续显示统一中文提示，不暴露内部异常名或 Telegram 原始错误文本。
- 登录成功后自动恢复因连接或授权失效而阻塞的订阅规则。

## 非目标

- 不改变订阅关键词、媒体匹配、游标或下载入队逻辑。
- 不在界面展示 Telethon 异常类型或服务器返回文本。
- 不持久化账号标识、会话内容、Telegram 原始异常文本或堆栈。
- 不修改 Telegram 登录方式、二维码流程或代理配置。

## 方案

采用“调度器异步回调统一会话处理器”的方案。调度器保持负责规则运行和规则状态，
控制器保持负责全局连接、服务绑定和登录窗口。两者通过一个明确的
`on_session_expired` 异步回调连接，避免让调度任务异常退出，也不依赖轮询规则状态。

### 安全授权原因码

为 `SessionExpiredError` 增加固定原因码，至少覆盖：

- `auth-key-duplicated`
- `auth-key-invalid`
- `auth-key-unregistered`
- `session-revoked`
- `not-authorized`
- `unknown`

网关只根据已知 Telethon 异常类生成原因码。异常对用户的字符串仍保持统一中文提示。
任何 Telegram 原始异常文本都不得进入日志、诊断指标或界面。

### 后台订阅到全局登录流程

`SubscriptionScheduler` 捕获 `SessionExpiredError` 后按以下顺序处理：

1. 将当前规则保存为 `auth_required`，清空下次运行时间并保留统一中文错误。
2. 通知规则列表刷新，使持久状态与界面一致。
3. 等待 `on_session_expired(error)`，进入控制器现有的全局会话失效流程。

控制器的会话失效处理增加异步并发保护。同一失效期间，即使搜索、诊断、下载或订阅
同时报告失败，也只执行一次会话清理、服务解绑和登录窗口展示。处理完成后继续保持
规则为 `auth_required`；新的登录成功后，现有 `resume_after_connection()` 将规则恢复为
`waiting`、安排立即运行并唤醒订阅调度器。

### 连接与授权双重验证

网关提供显式授权验证能力。验证必须发起轻量 Telegram 账号请求，并遵守现有错误映射：

- 返回有效账号：授权有效。
- 返回未授权：抛出原因码为 `not-authorized` 的 `SessionExpiredError`。
- 已知授权异常：抛出带对应安全原因码的 `SessionExpiredError`。
- 临时网络异常：仍按 `TransientNetworkError` 处理，不清除会话。

`ensure_telegram_online()` 的顺序调整为：先确保传输连接，再验证账号授权，最后才设置
“连接正常”和登录态。授权失效进入统一会话处理器；临时网络失败显示可重试状态，
不得误判为授权失效。

### 脱敏日志与诊断报告

统一会话处理器写入一条 warning 日志，仅包含固定原因码，例如：

```text
Telegram authorization expired (reason=auth-key-duplicated)
```

日志不得包含异常原文、账号、频道、手机号、API 凭据或会话内容。

健康诊断的 Telegram 检查在授权失效时继续使用统一中文摘要，并在报告中加入白名单字段
`authorizationReason`。该字段只能是本设计列出的固定原因码；诊断存储层必须验证字段名、
类型和值域。控制器在当前失效恢复周期内保留最近的安全原因码，供重新登录前运行健康诊断
时使用；成功登录后清除该内存状态。常规通过报告不包含该字段。

## 错误处理与并发

- 会话失效处理必须幂等，不能重复清除凭据、重复关闭调度器或重复创建二维码任务。
- 后台回调自身的非取消异常必须安全记录，不能让订阅调度主循环静默退出。
- `asyncio.CancelledError` 继续向上传播，保证应用关闭和任务取消语义不变。
- 规则状态先持久化再触发全局处理，确保应用在中途退出后仍能解释失败原因。
- 网络失败不清除会话；只有明确授权失败才进入重新登录流程。

## 测试策略

按测试驱动开发增加以下覆盖：

1. 网关把每种 Telethon 授权异常映射为正确安全原因码，并把未授权结果映射为
   `not-authorized`。
2. 调度器在持久化 `auth_required` 后调用异步会话失效回调，且调度主循环不崩溃。
3. 控制器对并发会话失效只执行一次清理和一次登录窗口展示。
4. 传输连接存在但授权无效时，不显示“连接正常”，并进入统一登录流程。
5. 临时网络错误保留会话并显示可重试状态。
6. 登录成功后清除最近授权原因，并恢复、唤醒受阻订阅。
7. 日志仅包含安全原因码；诊断报告接受白名单原因码并拒绝任意字符串。
8. 自动订阅、连接恢复、控制器、诊断、日志和完整测试套件均保持通过。

## 验收标准

- 后台订阅遇到授权失效后无需用户切换页面，登录窗口立即出现。
- 同一失效事件只触发一次全局清理和重新登录流程。
- 未验证账号授权时，任何页面都不显示“连接正常”。
- 重新登录后，原 `auth_required` 规则自动恢复并可继续检查。
- 界面不显示内部异常名；日志和诊断报告可区分安全授权原因码。
- 日志和诊断产物不包含 Telegram 原始异常文本或敏感账号、凭据、会话数据。
