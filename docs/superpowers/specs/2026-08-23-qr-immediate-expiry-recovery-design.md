# TG 快取二维码立即过期恢复设计

日期：2026-08-23
状态：已确认设计，待实施计划
目标版本：v0.18.1

## 1. 问题与证据

用户在 v0.18.0 登录时看到二维码刚出现，电脑端便立即显示“二维码已过期，正在刷新…”，无法完成扫码登录。

当前二维码生命周期由两个彼此独立的机制控制：

- `LoginDialog` 把 Telegram 返回的绝对 UTC 过期时间与本机墙上时钟比较，独立渲染倒计时和“已过期”文字。
- `AppController` 等待 Telethon 的二维码任务抛出 `TimeoutError`，随后调用 `recreate()` 并重新显示二维码。

界面没有在首次收到非正剩余时间时拒绝二维码，也没有在显示到期时向控制器提供去重的恢复信号。因此，只要界面层收到已经到期或接近到期的绝对时间，界面就会立即进入过期状态，而后台刷新是否及时发生取决于另一条异步链路。该分离状态是本次故障的根因。

诊断已确认：

- Windows UTC 时间与公网服务器时间偏差约 `0.121` 秒，不足以解释立即过期。
- 真实 Telegram 请求返回的二维码剩余有效期约 `29.39` 秒。
- 使用正式 `LoginDialog` 渲染真实二维码耗时约 `0.015` 秒，首次倒计时为正数。
- 真实 Telethon 等待任务在两秒后仍在运行。
- 真实控制器链路可在约三十秒后生成第二个二维码，两次有效期均约 `29` 秒且没有错误。

这些结果说明正常路径可用，但当前契约没有覆盖非正或过短有效期、墙上时钟跳变以及界面到期与后台刷新不同步的边界情况。

## 2. 目标

1. 电脑端不得首次显示一个已经过期或剩余时间不足以扫码的二维码。
2. 二维码有效期由一个统一的相对生命周期表示，界面倒计时不再持续依赖墙上时钟。
3. 二维码到期后必须自动刷新，并且手动刷新、Telethon 超时和界面兜底刷新不会并发创建多个令牌。
4. 等待监听应在二维码对用户可见前启动，缩小“先显示、后监听”的扫码竞态窗口。
5. 失败时提供可恢复操作和不含敏感信息的诊断证据。
6. 保持首次登录、候选账号重新登录、手机号验证码和两步验证流程兼容。

## 3. 非目标

- 不改变 Telegram API ID/API Hash 的获取流程。
- 不改变会话加密、候选账号原子切换或下载服务绑定协议。
- 不修改二维码视觉样式、尺寸或纠错等级。
- 不固定周期高频刷新有效二维码。
- 不在日志、诊断、测试快照或界面中记录二维码 URL、令牌、API Hash、手机号、验证码、密码或会话字符串。

## 4. 方案比较

### 4.1 统一有效期与去重恢复（采用）

网关在接收二维码时计算相对有效秒数；控制器拒绝过短令牌并有限重建；界面使用单调计时；界面到期只发出一次兜底刷新请求。该方案同时修复错误显示、失效令牌展示和刷新竞态。

### 4.2 只修改过期提示

把“已过期”改成“正在刷新”可以减少困惑，但不会阻止失效二维码被展示，也不能保证刷新任务存在，因此不采用。

### 4.3 固定每二十秒刷新

周期刷新可减少过期概率，但会使用户正在扫描的二维码提前失效，增加 Telegram 请求并制造更多竞态，因此不采用。

## 5. 组件设计

### 5.1 `QrLoginInfo` 相对有效期契约

`QrLoginInfo` 保留二维码 URL，并增加正数 `valid_for_seconds`。绝对 `expires_at` 可暂时保留用于兼容现有调用，但控制器和界面不得再以它作为倒计时的唯一依据。

`TelethonGateway._qr_info()` 在收到 Telegram 响应的同一时刻计算：

```text
valid_for_seconds = expires_at_utc - utc_now
```

网关接受可注入的 UTC 时钟用于确定性测试。计算结果允许为非正数，以便控制器识别并恢复；不得在网关层静默伪造有效期。

### 5.2 最小可展示有效期

控制器只展示剩余时间不少于五秒的二维码。`begin_qr_login()` 或 `refresh_qr_login()` 收到不足五秒的二维码时，立即调用一次 `recreate()` 获取新令牌。

一次用户操作最多接受一次额外重建。第二个令牌仍不足五秒时，不进入无限循环，显示固定错误：

```text
二维码有效期异常，请检查系统时间或网络后重试
```

界面保留“刷新二维码”和“改用手机号登录”作为恢复路径。

### 5.3 单调倒计时

`LoginDialog.show_qr()` 接收 `valid_for_seconds`，使用可注入的单调时钟记录本地截止点：

```text
deadline = monotonic_now + valid_for_seconds
remaining = ceil(deadline - monotonic_now)
```

单调时钟不受系统时间同步、时区调整或用户修改日期影响。首次剩余时间必须为正；控制器已拒绝不足五秒的令牌，界面不负责伪造或延长 Telegram 的实际有效期。

### 5.4 先监听、后显示

控制器取得可展示二维码后：

1. 增加二维码 generation。
2. 创建该 generation 的等待任务。
3. 让出一次事件循环，使 Telethon 注册登录令牌更新监听器。
4. 再把同一 generation 的二维码交给界面显示。

如果等待任务在显示前已经结束，控制器不得显示对应二维码，而是按结果进入成功、两步验证、自动刷新或错误处理。

### 5.5 到期兜底信号与去重

`LoginDialog` 增加 `qr_expired` 信号。单调倒计时首次到达零时：

- 停止当前倒计时定时器。
- 显示“二维码已过期，正在生成新二维码…”。
- 仅为当前展示 generation 发出一次 `qr_expired`。

控制器把界面信号、Telethon `TimeoutError` 和手动刷新都路由到同一个刷新入口。入口使用现有二维码 generation 和一个刷新锁实现以下规则：

- 同一 generation 最多刷新一次。
- 较旧 generation 的超时或界面信号直接忽略。
- 手动刷新会使旧 generation 失效并取消旧等待任务。
- 刷新过程中重复点击按现有异步动作策略去重。

### 5.6 登录上下文隔离

所有二维码操作继续通过 `_login_gateway()` 获取网关：

- 首次登录使用当前未授权网关。
- 明确重新登录使用候选网关。
- 取消候选登录只销毁候选网关和候选等待任务。
- 当前已授权账号、下载调度器、内容服务和订阅服务不得因二维码过期或刷新被断开。

## 6. 数据流

```text
用户明确发起登录
→ 网关请求 Telegram 登录令牌
→ 计算相对有效秒数
→ 控制器验证五秒安全阈值
→ 启动并确认等待监听
→ 界面按单调截止点显示二维码和正数倒计时
→ 扫码成功 / 需要两步验证 / 到期
→ 到期统一进入 generation 去重刷新
→ 新令牌重复上述流程
```

## 7. 错误与诊断

日志只记录以下非敏感字段：

- 事件名称：`qr-created`、`qr-rejected-short-ttl`、`qr-refresh-started`、`qr-refresh-deduplicated`、`qr-wait-failed`。
- 取整后的剩余秒数。
- generation。
- 登录上下文：`initial` 或 `candidate`。
- 异常类型；不得记录原始 Telegram 错误文本，除非已经通过现有安全映射。

网络失败继续显示现有安全错误。短有效期连续两次出现时停止自动重试，避免请求风暴。窗口关闭、切换手机号、修改凭据和应用退出继续取消等待及刷新任务。

## 8. 测试设计

### 8.1 网关测试

- 感知时区和无时区过期时间都转换为 UTC。
- `valid_for_seconds` 使用注入时钟计算。
- 过去时间得到非正有效秒数，不被伪装为有效。
- 二维码 URL 不出现在日志或失败信息中。

### 8.2 控制器测试

- 首个令牌不足五秒时不显示并立即重建一次。
- 第二个令牌有效时只显示第二个二维码。
- 连续两个短有效期令牌显示固定错误且不循环。
- 等待监听已开始后才调用界面显示。
- Telethon 超时和界面到期同时发生时只刷新一次。
- 手动刷新取消旧等待任务并使旧 generation 失效。
- 候选登录过期不会断开当前已授权网关或在线服务。
- 成功、两步验证、手机号备用和取消路径保持通过。

### 8.3 界面测试

- `show_qr()` 首次显示正数倒计时。
- 修改墙上时钟不影响单调倒计时。
- 到零时只发出一次 `qr_expired` 并停止定时器。
- 显示新 generation 后可重新倒计时并再次独立到期。
- 页面切换和关闭继续清除二维码与计时状态。

### 8.4 验证层级

1. 二维码网关、控制器和登录窗口定向测试。
2. 全部测试与 Ruff 静态检查。
3. 使用真实 Telegram API 进行不输出令牌的生成、等待、到期自动刷新验证。
4. 便携版与安装版冒烟测试。

## 9. 验收标准

- 新二维码首次展示时必须显示至少五秒的正数倒计时。
- 任何非正或过短令牌不得出现在界面。
- 到期后界面在一次刷新周期内恢复为新二维码和正数倒计时，不长期停留在“已过期”。
- 同一 generation 不产生重复刷新请求或多个并行等待任务。
- 登录成功后会话正常保存；取消和失败不破坏现有账号。
- 测试、日志、截图和发布证据均不包含登录敏感信息。
