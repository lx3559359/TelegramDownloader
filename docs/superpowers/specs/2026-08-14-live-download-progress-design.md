# Telegram 下载实时进度修复设计

日期：2026-08-14
目标版本：0.2.3（本地候选版本）

## 问题与证据

下载任务提交后，调度器和下载器会正常运行，并在项目内数据库中持续更新任务与媒体项状态；但控制器只在任务提交时和整个任务结束后调用 `refresh_tasks()`。因此下载期间界面一直保留最初的“等待中、0 / N、0 B/s”，右侧也显示“暂无活动任务”。

现场任务已成功下载 79,618 字节图片和 29,107,777 字节视频，数据库最终状态为 `completed`，证明故障位于界面刷新链路，而不是 Telegram 链接解析、账号会话、队列调度或媒体传输。

## 已确认方案

采用仅在任务运行期间生效的 0.5 秒周期刷新。任务开始时启动刷新，任务结束、暂停或失败后停止该任务的刷新。多个并发任务共享刷新节流，避免重复高频读取数据库。

不改变 Telegram 会话、下载文件格式、断点续传规则、数据库结构或在线更新协议。

## 组件与数据流

1. `MediaDownloader` 继续每 0.5 秒把已下载字节数和媒体项状态写入项目内 SQLite 数据库。
2. `AppController` 在调度器任务运行期间周期调用 `refresh_tasks()`，读取最新任务与媒体项快照。
3. 控制器根据相邻两次快照的字节差和时间差计算任务速度；已知总大小时计算预计剩余时间。
4. `TaskSummary` 携带显示文本及右侧概览所需的数值字段：完成项数、总项数、已下载字节、总字节、速度和剩余秒数。
5. `MainWindow.set_task_summaries()` 同步更新表格和右侧概览：
   - 活动任务显示真实标题和当前状态；
   - 进度条按已下载字节/总字节计算，未知总大小时退回已完成项数/总项数；
   - 总速度为所有下载中任务速度之和；
   - “已完成”和“队列剩余”按媒体项数量统计。

## 生命周期与并发

- 新任务提交后最多 0.5 秒内从“等待中”更新为“下载中”。
- 下载完成后执行最后一次强制刷新，确保界面显示“已完成”。
- 暂停、失败、重试和程序退出沿用现有调度器状态；刷新循环不拥有下载任务，也不会影响下载取消与断点续传。
- 并发任务可以各自等待调度器，但界面刷新通过控制器节流到最多每 0.5 秒一次。
- 速度样本只保存在内存中，退出程序后无需持久化，不在 C 盘产生数据。

## 错误处理

- 下载异常仍由现有调度器安全转换为暂停、等待重试或部分失败状态。
- 周期刷新不吞掉调度器异常；后台任务仍通过现有 `_background_finished()` 记录安全错误并反馈状态栏。
- 无法计算速度或剩余时间时显示 `—`，不显示误导性的负数或无穷值。
- 已完成任务速度归零，并清理对应的内存速度样本。

## 测试与验收

先写失败测试，再实施修复：

1. 控制器测试：调度器仍在运行时，窗口已经收到“下载中”快照，而不是必须等到任务结束。
2. 控制器测试：相邻进度快照能够生成非零速度和合理剩余时间；任务结束后执行最终刷新。
3. 界面测试：活动任务会更新右侧标题、进度条、总速度、完成数和剩余数。
4. 并发测试：多个活动任务不会让数据库刷新频率超过每 0.5 秒一次。
5. 回归测试：暂停、恢复、失败、程序关闭和原有 188 项测试保持通过。
6. 打包验收：生成 0.2.3 直接启动目录、便携 ZIP 和安装包；运行 EXE 自检与安装/升级/卸载冒烟测试；确认设置、DPAPI 登录会话和任务数据库在重建前后保持一致。
