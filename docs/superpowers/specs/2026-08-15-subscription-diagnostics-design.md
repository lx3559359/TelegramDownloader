# 自动订阅诊断中心设计

## 背景与目标

v0.5.0 已能稳定地增量检查新消息并把匹配媒体加入下载队列，但当一次检查没有新增任务时，用户只能看到“扫描、匹配、新增、重复”的最近汇总，无法快速判断是没有新消息、关键词未命中、媒体类型不符，还是媒体已存在。现有数据库已经保留每条规则最近 100 次运行记录，但界面没有展示它们。

本轮把自动订阅从“能运行”提升到“可解释、可验证”：选中规则后展示详细配置和运行历史，并允许只读测试最近消息。测试不会移动增量游标、创建下载任务、写入运行历史或修改规则，因此可以安全地验证关键词和媒体类型。

成功标准：

- 选中规则后可以查看配置、最近错误和最近 20 次运行记录。
- 每次运行结果给出可读结论，包括无新消息、关键词未命中、媒体类型不符、全部重复或已新增任务。
- 用户可以测试目标会话最近 100 条消息，并看到关键词命中数、媒体匹配数、已存在数和最多 20 个媒体样本。
- 测试期间有明确进度和取消入口；重复点击不会启动第二个测试。
- 取消、断网、限流、登录失效或群组不可用不会修改规则、游标、任务和运行历史。
- 自动检查继续让前台测试优先，界面在测试时保持可响应。
- 所有业务数据、临时文件和日志仍位于应用目录。

## 方案比较

### 方案 A：诊断详情和只读探测（采用）

复用已有运行记录，新增长度受限的最近消息读取和纯只读规则探测。实现范围可控，不改变自动下载语义，并直接解决“为什么没有下载”的问题。

### 方案 B：允许规则历史补抓

用户可以选择补抓最近若干条旧消息，但这会引入大批量下载确认、游标语义、重复任务和误操作恢复等问题。它适合在诊断稳定后单独设计，本轮不采用。

### 方案 C：跨群组全局搜索

一次搜索所有已加入群组，价值较高，但需要独立的多会话分页、限流、公平调度、聚合历史和结果持久化模型。本轮不把它与订阅诊断耦合。

## 用户体验

“自动订阅”页面保留现有规则表，在下方增加选中规则详情区：

- 规则摘要：群组、关键词、媒体类型、检查间隔、状态、最近错误和下次检查时间。
- 运行历史：最近 20 次，列出完成时间、结果、扫描、关键词命中、媒体匹配、新增、重复和安全错误。
- 操作：“测试最近 100 条”。只有已登录、选中规则且没有其他订阅前台动作时可用。

测试开始后显示确定的已扫描计数、关键词命中数和媒体匹配数，并提供“取消测试”。完成后在非模态详情区显示：

- 一句首要结论，例如“最近 100 条中没有出现关键词”“命中 3 条消息，但没有所选媒体类型”或“匹配 4 项，其中 4 项已在队列”。
- 最多 20 个样本，列出日期、类型、文件名、大小、是否已存在和不超过 80 个字符的消息摘要。
- 测试样本只保存在内存中；切换账号、退出应用或再次测试时清除。

规则表中的“最近结果”改用统一解释器生成简短文本。没有新增任务不再被笼统显示成零统计。

## 领域模型与解释规则

新增纯领域对象：

- `SubscriptionProbeProgress`：规则 ID、已扫描消息数、关键词命中消息数、匹配媒体数和阶段。
- `SubscriptionProbeSample`：消息 ID、UTC 日期、媒体类型、文件名、大小、已存在状态和安全摘要。
- `SubscriptionProbeReport`：规则 ID、扫描数、关键词命中数、匹配媒体数、已存在数、样本和完成时间。

`SubscriptionRun` 增加 `keyword_hits`，使正式自动检查也能区分关键词和媒体类型。catalog schema 从 v2 幂等迁移到 v3，为 `subscription_runs` 增加非空、默认值为 0 的 `keyword_hits`；旧运行记录保持可读，显示为 0。规则表结构不变。

统一解释规则按以下优先级生成文本：

1. 运行失败：显示脱敏错误类型或安全错误文本。
2. 扫描数为 0：没有新消息。
3. 关键词命中为 0：新消息未命中关键词。
4. 媒体匹配为 0：关键词已命中，但没有所选媒体类型。
5. 新增为 0 且重复等于媒体匹配：匹配项均已在队列。
6. 其他成功情况：显示新增和重复数量。

## Telegram 最近消息读取

`TelegramGateway` 增加窄接口 `recent_messages(entity_ref, *, limit)`，限制为 `1..100`。Telethon 实现按从新到旧读取，再转换成从旧到新的 `RemoteMessage` 元组，便于复用现有相册和确定性过滤逻辑。网关只负责读取和转换，不负责探测统计、持久化或 UI 文本。

读取遵守现有实体解析、错误映射和权限边界，不自动加入群组，不绕过内容保护，也不输出完整消息正文。

## 只读探测服务

`SubscriptionService.probe_rule(rule_id, on_progress=None)` 执行以下流程：

1. 从当前账号读取规则并确认在线。
2. 固定读取最近最多 100 条消息。
3. 使用与正式运行完全相同的关键词标准化、媒体类型过滤、相册展开和媒体键去重。
4. 统计关键词命中消息数、允许媒体数和已存在任务数。
5. 只保留最多 20 个样本；摘要在内存中裁剪，不写日志和数据库。
6. 返回报告，不调用 planner commit，不推进游标，不保存 `subscription_runs`。

为了防止正式运行与探测规则逐渐产生不同结果，关键词匹配、相册展开和媒体去重提取为服务内共享的私有纯逻辑。探测使用 `TaskPlanner.existing_media_keys` 判断是否已存在，但不得创建任务。

## 正式运行统计

正式 `run_rule` 在现有 `inspected`、`matched`、`queued` 和 `duplicate` 之外记录 `keyword_hits`。关键词命中按消息计数，相册中的多项媒体仍按媒体数计入 `matched`。失败、取消和未知异常继续保留安全游标，并沿用现有行为把完成、失败或取消结果写入运行历史；`keyword_hits` 保存异常发生前已经确定的计数。

历史每条规则仍最多保留 100 次，页面只加载最近 20 次，避免大量 UI 对象。删除规则继续级联删除运行历史，但不删除任务和文件。

## 调度、控制器与取消

控制器新增单个 `_subscription_probe_task`：

- 测试属于前台 Telegram 操作，`foreground_telegram_busy()` 在测试期间返回真，后台调度器延后执行。
- 同一时间只允许一个测试；重复请求只聚焦当前进度，不创建新任务。
- 切换账号、登出、关闭程序或用户点击取消时取消并等待该任务。
- 完成、失败或取消都在 `finally` 恢复按钮、清理进度，并重新加载选中规则详情。

页面新增 `rule_selected(str)`、`probe_requested(str)` 和 `probe_cancel_requested()` 信号。页面只展示传入的运行历史、进度和报告，不访问 catalog 或 Telegram。

## 错误处理与隐私

- 离线：测试按钮禁用，历史仍可查看。
- 短暂断网：显示可重试错误，不触发后台退避计数，不改变规则状态。
- FloodWait：显示平台要求的等待时间，不自动循环探测。
- 登录失效：交给现有会话失效流程，规则和历史保留。
- 群组不可用：显示访问错误，不自动暂停规则；正式调度的现有策略保持不变。
- 取消：显示“测试已取消”，不作为失败写日志或历史。

日志只记录动作类型、规则 ID 的内部引用和错误类别，不记录 API Hash、Session、完整手机号、群组名、关键词、文件名或消息摘要。探测报告仅存在于当前进程内存。

## 数据与磁盘边界

唯一持久化变更是应用目录 `data/database/catalog.sqlite3` 的 schema v3 和正式运行新增的 `keyword_hits` 计数。探测不创建数据库表、缓存、缩略图或临时媒体文件。现有 `PortablePaths`、构建脚本、安装器和在线更新数据保留协议不变。

## 测试与验收

自动化覆盖：

- v2 到 v3 迁移、旧历史默认值和新计数往返。
- 最近消息读取的数量边界、顺序、空会话和错误映射。
- 探测与正式运行共享关键词、媒体类型、相册和去重语义。
- 探测不推进游标、不创建任务、不保存运行历史。
- 正式运行保存 `keyword_hits`，解释器覆盖六种结论。
- 历史模型、规则选择、测试进度、取消、重复点击抑制和离线状态。
- 控制器前台优先、账号切换、异常恢复和安全关闭。
- self-test 报告 schema v3，所有路径仍位于应用目录。

真实账号 QA 使用项目内加密会话的隔离副本：创建随机唯一关键词规则，验证最近 100 条测试、取消、重复点击、正式立即检查、历史显示、重启恢复和临时规则清理。随机关键词确保不创建真实下载任务；验证前后任务数必须一致。最后运行完整 pytest、Ruff、便携包自检、安装包升级/卸载保留和 ZIP 隐私检查。

## 版本与范围

本地候选版本提升为 v0.6.0。README 和发行说明解释诊断只读、最近 100 条、最多 20 个样本、运行历史和不影响自动游标的保证。

本轮不包含历史补抓、跨群组全局搜索、复杂布尔关键词、缩略图探测预览、Windows 后台服务、带宽限速或外部通知。线上 stable 指针和公开资产仍只在独立发布流程中更新。
