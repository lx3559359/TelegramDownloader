# 高级订阅规则设计

状态：已由用户确认。本文只定义 P1 第 5 项“高级订阅规则”；批量链接导入、全局媒体调度和下载目录/命名模板继续按既定顺序在后续独立设计中完成。

## 1. 目标

把现有“每条规则只有一个关键词、只检查创建后的新消息”扩展为结构化订阅规则：

- 每条规则支持多个包含词；
- 包含词可选择“任意命中（OR）”或“全部命中（AND）”；
- 支持多个排除词，任意排除词命中即淘汰该消息；
- 创建或实质修改规则时，可选择不补抓或补抓最近 1、3、7、30 天；
- 补抓可分页、取消、失败重试并跨进程重启续跑；
- 原有单关键词订阅无损迁移，既有游标、启停状态、运行历史和任务去重语义保持不变。

本功能继续依赖主程序或托盘后台进程运行，不引入 Windows 服务。

## 2. 用户可见语义

### 2.1 包含与排除

编辑器提供“包含词”和“排除词”两个多行输入框，每行一个词组。包含词至少 1 个、最多 20 个；排除词可为空、最多 20 个。单个词组去除首尾空白后长度为 1–100 个字符，全部词组合计不超过 2,000 个字符。

匹配前对消息文本和词组执行 Unicode `casefold`，并把连续空白折叠为一个空格。匹配仍是词组子串匹配，不做分词、词干还原、正则表达式或模糊匹配。例如 `AI model` 可以匹配 `New AI   Model released`。

归一化后重复的词组只保留第一次出现的显示形式。相同词组不能同时出现在包含和排除列表；界面在保存前给出明确错误。

匹配顺序固定：

1. 根据选择的模式计算包含词；
2. OR 模式下任意包含词出现即通过，AND 模式下全部包含词出现才通过；
3. 若任意排除词出现，无条件淘汰；
4. 通过文本规则后再应用媒体类型过滤；
5. 相册仍以命中消息为入口完整展开，但只保留所选媒体类型。

排除词始终使用 OR 语义，不受包含词 AND/OR 选择影响。

### 2.2 历史补抓

历史范围固定为“不补抓、最近 1 天、最近 3 天、最近 7 天、最近 30 天”。时间以 UTC 持久化，以创建或实质修改规则的时刻向前计算，界面使用 Windows 当前时区展示说明。

“实质修改”包括来源会话、包含词、排除词、AND/OR、媒体类型或历史范围变化。仅修改检查间隔或暂停/继续不会重置游标。

- 不补抓：保存时把当前最新消息设为基线，只处理之后的新消息，与旧版一致。
- 选择历史范围：保存时固定一个截止消息 ID，并定位所选时间起点之前的最后一条消息作为游标；随后从旧到新每批最多扫描 500 条，直至固定截止 ID。
- 补抓期间到达的新消息不扩大当前补抓范围，在补抓完成后的下一次正常增量检查中处理。
- 每批成功提交任务后才推进游标；取消、崩溃或网络失败不会跳过未处理消息。
- 规则重启后从已持久化的游标、起始时间和固定截止 ID 继续，不重复扫描已完成页；已有媒体仍由统一规划器在预检和提交时去重。

历史范围是规则的配置项，但不会在每次定时检查时反复回扫。它只在新建或发生实质修改时触发一次补抓。

### 2.3 展示与诊断

规则列表和详情使用简洁摘要，例如“任意：AI、模型；排除：广告；最近 7 天”。摘要过长时在表格中省略，完整规则在详情区可读。

“只读测试最近 100 条”与实际运行共用同一个匹配器，但不会触发历史补抓、推进游标、创建任务、修改规则或写入运行历史。

现有诊断计数 `keyword_hits` 的数据库字段保留兼容，用户界面统一改称“规则命中”：只有同时通过包含和排除判定的消息才计数。媒体类型不匹配仍单独体现在“规则命中”与“媒体匹配”的差值中。

## 3. 领域模型与模块边界

新增聚焦模块 `subscription_matching.py`，只负责：

- `SubscriptionMatchMode`：`ANY` 与 `ALL`；
- `SubscriptionCriteria`：不可变的包含词、排除词和模式；
- 词组归一化、验证、稳定摘要与稳定指纹；
- `matches(text)` 的纯函数判定。

`subscriptions.py` 继续承载订阅生命周期模型，但 `SubscriptionDraft` 和 `SubscriptionRule` 改为持有结构化 `criteria`，并增加：

- `history_days: int`，仅允许 `0, 1, 3, 7, 30`；
- `backfill_from_utc: datetime | None`，记录待初始化或正在执行的固定历史起点；
- `backfill_through_id: int | None`，记录本轮补抓的固定截止消息 ID。

界面、服务、列表模型和任务规划器不再自行解析关键词。所有实际匹配、摘要和指纹都调用 `SubscriptionCriteria`，避免只读测试与后台执行出现不同语义。

任务规划器接收稳定的规则摘要作为任务来源描述，但媒体身份去重键仍是 `(peer_ref, message_id, media_id)`，不会因规则表达式变化而重复下载。

## 4. 数据库兼容与迁移

内容目录 schema 从 4 升到 5。`subscription_rules` 增加结构化字段：

- `include_keywords_json TEXT NOT NULL`；
- `exclude_keywords_json TEXT NOT NULL`；
- `match_mode TEXT NOT NULL`；
- `matcher_fingerprint TEXT NOT NULL`；
- `history_days INTEGER NOT NULL`；
- `backfill_from_utc TEXT`；
- `backfill_through_id INTEGER`。

旧 `keyword` 和 `normalized_keyword` 列暂时保留为向后兼容桥：`keyword` 保存稳定可读摘要，`normalized_keyword` 保存与 `matcher_fingerprint` 相同的规范指纹，以继续满足旧唯一约束。运行时的唯一事实来源是结构化 JSON 与 `match_mode`，业务逻辑不再从摘要反向解析。

迁移在同一个 SQLite 事务内逐行完成：每条旧规则转换为“一个包含词、无排除词、OR、不补抓”，保留原有 `last_message_id`、状态、时间、错误和失败次数。旧规则指纹按新规范重新计算。迁移失败则整个事务回滚，schema 版本不前进。

同一账号和会话中，规范化后完全相同的“模式 + 包含词集合 + 排除词集合”视为重复规则；词组输入顺序不影响指纹。媒体类型、检查间隔和历史范围不参与重复身份，因为它们可直接编辑。

## 5. Telegram 网关与补抓数据流

网关接口新增只读方法 `message_id_before(entity_ref, before_utc)`，返回指定 UTC 时刻之前最后一条可见消息的 ID；没有更早消息时返回 0。Telethon 适配器使用服务端日期游标定位，不下载媒体内容。

新建或实质修改规则时：

1. 先以 `BASELINING` 状态保存规则和固定 `backfill_from_utc`；
2. 读取当前最新消息 ID；
3. 不补抓时直接保存该 ID 为 `last_message_id`；
4. 需要补抓时读取时间边界 ID，把它保存为 `last_message_id`，并把步骤 2 的快照保存为 `backfill_through_id`；
5. 将规则置为 `WAITING`，补抓规则立即到期，无补抓规则按正常间隔到期。

若基线阶段失败，规则进入现有失败/退避流程，但保留 `backfill_from_utc`，重试时仍使用原始时间起点，不会悄悄缩短用户选择的范围。

运行规则时，若 `backfill_through_id` 存在，则本页 `through_id` 固定使用它；否则读取正常增量快照。每页沿用现有 500 条上限、相册展开、规划器双重去重和运行历史。到达固定截止 ID 后，在同一事务语义中清空两个临时补抓字段，下一轮转入正常增量。

## 6. 编辑器与交互

订阅编辑器保持单个对话框，不引入表达式语言：

- “包含词”使用可换行文本框，并在旁边选择“任意一个（OR）”或“全部（AND）”；
- “排除词”使用可换行文本框，明确提示“命中任意一个即排除”；
- “历史补抓”使用固定下拉选项；
- 基线说明会随选项变化，明确显示“不补抓旧消息”或“保存后补抓最近 N 天”；
- 编辑既有规则时，若实质配置变化，保存前说明会重建本次补抓基线，但已下载文件和已有任务不会删除；
- 离线时仍可查看规则与运行历史，但新建、编辑、立即检查和只读测试沿用现有禁用规则。

保存失败时对话框保持打开并显示可操作错误。界面不显示数据库指纹、原始 Telegram 异常或完整内部堆栈。

## 7. 错误、取消与隐私边界

- 本地字段错误在访问 Telegram 前拒绝，避免建立半成品规则。
- 网络、限流、权限和登录失效继续走现有分类、退避和重新登录路径。
- 页面扫描或任务提交失败不推进游标；运行记录保存固定错误类型，不保存消息正文或规则命中内容。
- 取消只读测试不会影响规则；取消实际调度在安全边界保留当前补抓状态。
- 系统通知仍只报告聚合的订阅命中数量，不包含包含词、排除词、会话名称、消息、文件名或路径。
- 数据继续只写入应用目录中的现有目录数据库，不新增系统级权限或外部服务。

## 8. 测试与验收

### 8.1 自动化

- 纯匹配器覆盖 OR、AND、排除优先、大小写、连续空白、Unicode、重复词、包含/排除冲突、数量和长度边界。
- 指纹覆盖词组顺序无关、模式/排除变化有别，摘要不参与匹配。
- schema 4 到 5 迁移覆盖旧单关键词、游标、暂停状态、运行历史保留和事务回滚。
- 新建规则覆盖不补抓及 1/3/7/30 天基线；网关边界覆盖无历史、恰好边界、跨时区展示不影响 UTC 数据。
- 补抓覆盖多页、固定截止、补抓期间新消息、取消、网络失败、重启续跑、最后一页切回正常增量和重复媒体。
- 编辑覆盖仅间隔变化不重置，以及来源、条件、媒体或历史范围变化按选项重新建立基线。
- 实际运行与只读测试对同一消息集合产生相同规则命中结果。
- UI 覆盖字段回填、验证、动态说明、规则摘要、离线只读和保存失败不关闭。
- 运行记录和通知覆盖“规则命中”文案与隐私字段扫描。
- 完整 pytest、Ruff、源码自检、冻结程序和安装器升级/卸载数据保留冒烟全部通过。

### 8.2 Windows 交互验收

- 创建 OR、AND、排除规则，并用只读测试确认结果与实际立即检查一致。
- 创建“不补抓”和“最近 1 天”规则，验证前者只处理新消息，后者补抓范围内消息且不越界。
- 补抓中退出并重启，验证从持久游标继续且任务不重复。
- 编辑检查间隔不重扫；编辑条件或历史范围按新配置补抓。
- 旧数据库升级后，原单关键词订阅的启停状态、游标和运行历史可见且行为不变。

## 9. 验收标准

1. 一条规则可保存并正确执行 1–20 个包含词、0–20 个排除词和 AND/OR 模式。
2. 排除词优先，后台执行和只读测试使用同一匹配器并得到一致结果。
3. 用户可选择不补抓或最近 1、3、7、30 天，补抓不越过固定起止范围。
4. 多于 500 条的补抓渐进执行，并在失败、取消和进程重启后不丢失或重复推进。
5. 实质修改触发一次新基线；仅改间隔、暂停或继续不重置游标。
6. schema 4 的单关键词规则无损升级，既有游标、状态、运行历史和任务保持兼容。
7. 规则命中计数、详情摘要和运行解释准确，通知不泄露规则文本或内容元数据。
8. 完整自动化、打包冒烟和规定的 Windows 交互验收有可追溯证据。

## 10. 本轮不包含

- 括号、嵌套布尔表达式、每个词独立选择 AND/OR；
- 正则表达式、通配符、模糊匹配、同义词、词距或自然语言规则；
- 自定义日期时间、按消息条数补抓或无限全历史补抓；
- 单条规则跨多个会话；
- 批量链接导入、跨任务媒体槽和下载命名模板。
