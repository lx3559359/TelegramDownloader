# TelegramDownloader v0.8.0 启动、去重与正式发布设计

日期：2026-08-16

状态：已按用户的持续目标模式与“后续按建议执行、不再询问”授权定稿

## 目标

从本地 v0.7.0 出发，修复真实审计发现的普通链接重复入队风险，改善未签名 PyInstaller 运行时冷启动期间缺少反馈的问题，降低大任务下载状态更新时的数据库读取量，并把包含 v0.5.0–v0.8.0 功能的正式版安全发布到 GitHub 与魔搭双源。

所有应用业务数据继续只保存在应用目录；不新增 Windows 服务、计划任务、注册表配置、系统凭据或用户目录业务文件。

## 审计证据

- v0.7.0 基线 462 项测试和 Ruff 通过。
- 已保存 DPAPI 会话可直接连接，账号授权成功并同步到 4 个已加入会话，没有触发二维码。
- 用户之前提供的单条消息链接在隔离目录扫描出 2 项，约 29.19 MB；真实下载全部完成、大小一致、任务状态完成，所有路径均位于项目内 QA 根目录。
- 双源在线更新检查均有效；本地 0.7.0 面对公开 0.4.0 正确返回“无更新且未阻断”。
- 冷启动首次主窗口可见接近一分钟，热启动约 13.1 秒。分段计时显示控制器启动约 0.44 秒、窗口显示约 0.60 秒，延迟主要位于完整应用模块导入和应用对象构建；当前在这些阶段完成前没有任何可见反馈。
- `TaskPlanner.scan()` 明确传入 `skip_existing=False`，`commit()` 使用非去重的 `create_task()`；搜索和订阅入口则使用 `create_task_deduplicating()`。因此普通链接重复扫描与确认可以绕过全局媒体去重，并生成改名后的重复文件。
- `DownloadScheduler._set_item_state()` 为读取一个媒体项的当前字节数调用 `list_items(task_id)`，每次状态切换都会加载整个任务明细；任务媒体数增长后形成不必要的 O(N) 查询。
- 实际内容搜索在连续网络审计后收到 Telegram FloodWait；现有服务已将其安全转换为等待秒数并把搜索标记为未完成，因此本轮不把平台限流误判为应用缺陷。

## 方案比较

### 方案 A：启动反馈、全局去重和热点查询优化（采用）

在正常 GUI 启动路径中先创建一个极小的 Qt 启动画面，再导入完整应用；普通扫描预览先过滤已存在媒体，提交时继续使用数据库原子去重防竞态；调度器只查询目标媒体项。改动集中、风险可控，直接覆盖已复现问题。

### 方案 B：诊断中心与脱敏支持包

增加连接、数据库、更新源和磁盘状态页面。它能提升排障能力，但不能阻止重复下载，也不能解决启动期间“无响应”的第一感受，延后到后续版本。

### 方案 C：限速、时段调度和系统通知

会引入新的持久配置、调度状态和 Windows 集成边界，测试面明显扩大。本轮以正式发布已有高价值功能为主，不纳入。

## 设计

### 1. 尽早显示启动反馈

新增一个只依赖 PySide6 的小型启动组件。正常 GUI 启动在解析命令行和重定向项目内 TEMP/APPDATA 后立即创建 `QApplication` 与启动画面，再导入完整 `telegram_downloader.app`。

启动画面使用程序绘制的纯色背景和文字，不依赖网络、磁盘外资源或新图片文件。它依次显示：

1. 正在加载运行组件；
2. 正在准备本地数据；
3. 正在恢复任务与账号。

`--self-test` 和 `--update-health-check` 继续走无界面路径，不创建启动画面。已有单实例守卫仍是唯一实例判定来源；第二实例或启动异常必须关闭启动画面。`create_application()` 复用已经存在的 `QApplication`。

主窗口创建完成后先 `show()` 并结束启动画面，再运行 `controller.start()`。控制器仍在同一个 qasync 事件循环中初始化任务、缓存账号、后台更新检查和会话恢复；这些步骤不得阻止主窗口首次可见。启动失败时保留安全错误处理和正常关闭语义。

### 2. 普通链接使用全局原子去重

`TaskPlanner.scan()` 在构建预览时查询现有媒体键，只展示尚未入队的媒体。需要区分两种空结果：

- Telegram 返回范围内没有媒体：继续提示“没有找到可下载媒体”；
- Telegram 返回媒体但全部已存在：提示“媒体已全部存在于下载队列”。

预览与用户确认之间仍可能发生并发入队，所以 `TaskPlanner.commit()` 也必须委托 `create_task_deduplicating()`，不能再调用 `create_task()`。`commit()` 的返回值明确改为现有的 `SelectedCommit`，向控制器报告实际接受键和竞态跳过数；`commit_selected()` 保留为同一原子提交实现的兼容入口，避免两套去重逻辑。

控制器只在至少接受一项时启动任务，并显示“加入 N 项、跳过重复 M 项”。全部在提交瞬间变为重复时，不创建空任务、不启动调度器，并显示安全、可理解的结果。

搜索、自动订阅、普通频道扫描、单条消息和相册最终共享相同的数据库去重事实：`(peer_ref, message_id, media_id)`。归档任务继续保留媒体行，因此仍参与去重。

### 3. 调度器使用单媒体查询

`SchedulerRepository` 增加已有仓库能力 `get_item(item_id)`。`DownloadScheduler._set_item_state()` 只读取目标媒体项的最新 `downloaded_bytes`，不再通过 `list_items(task_id)` 加载整项任务。

任务最终汇总仍允许使用 `list_items()`，因为它需要判断整项任务的完成/失败状态；单媒体状态切换不需要整表数据。此改动不改变重试次数、暂停、断点偏移或错误脱敏语义。

### 4. 版本与正式发布

版本统一提升为 0.8.0。发行说明必须明确：

- 启动阶段立即提供可见反馈，主窗口不再等待会话恢复；
- 普通链接、相册、搜索和订阅统一全局去重；
- 下载状态热点查询从整任务扫描降为单媒体读取；
- v0.5.0 自动订阅、v0.6.0 诊断和 v0.7.0 任务管理首次进入公开 stable。

发布流程继续使用项目内 Ed25519 私钥、SHA-256、GitHub 草稿和魔搭候选两阶段事务。两个远程候选逐字节回下载比较成功后，先推进魔搭指针，再发布 GitHub latest；任一阶段失败按现有事务回滚。

## 错误处理

- 启动画面创建失败时回退到现有启动路径，不能阻止程序运行。
- 应用导入、创建或事件循环启动异常时关闭启动画面并保持非零/现有异常语义。
- 全部媒体在预览前重复时不弹确认框；确认后竞态重复时不创建空任务。
- 去重错误不得暴露频道名、文件名、目标路径、会话或 Telegram 原始异常。
- FloodWait、网络断开和权限错误继续使用现有安全提示与恢复策略。

## 数据与隐私边界

- 启动画面不持久化任何状态。
- 去重只读取应用目录下 `data/database/tasks.sqlite3`，不建立新数据库或外部索引。
- 下载文件继续位于 `<应用目录>/downloads`；设置、会话、日志、缓存、临时文件和更新暂存继续位于 `<应用目录>/data`。
- QA 只使用项目内隔离会话副本，提交和发布包不得包含账号、群组、消息、搜索词、文件名、数据库、日志、下载文件或截图。
- 正式便携 ZIP 必须对 `data/`、`downloads/`、会话、密钥、数据库和日志保持零命中。
