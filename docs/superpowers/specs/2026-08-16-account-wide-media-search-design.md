# Telegram 全账号资源搜索设计

日期：2026-08-16
目标：在不选择具体群组的情况下，搜索当前账号可访问的全部 Telegram 云端会话资源，同时保留现有单会话搜索能力。

## 已确认范围

- 搜索范围覆盖当前账号可访问的群组、频道、私聊、机器人会话、收藏夹以及已归档会话。
- 全账号搜索与单会话搜索并存；用户不需要逐个选择或逐个扫描会话。
- 结果数量上限按全账号合计，不按每个会话分别计算。
- 搜索仍要求非空关键词，并继续应用日期范围、媒体类型和结果数量上限。
- 结果只包含可下载媒体；纯文本命中不进入结果列表。
- 跨会话结果按消息时间倒序汇总，并明确显示真实来源。
- Telegram 秘密聊天、不再可访问的历史、已被服务端删除的消息以及 Telegram API 不返回的内容不在可搜索范围内。

## 不在本轮范围

- 不下载并建立完整聊天历史或本地全文索引。
- 不提供离线发起新搜索；离线时仍只能查看已经保存的搜索记录。
- 不绕过 Telegram 权限、会话访问限制或服务端搜索规则。
- 不把全账号搜索扩展为自动订阅规则；现有自动订阅仍绑定单个群组或频道。
- 不改变更新发布边界；实现和本地验证不代表自动发布新版本。

## 方案选择

采用 Telegram 服务端全局搜索，基于 Telethon 1.44.0 对 `messages.searchGlobal` 的支持实现。

未采用的方案：

1. 逐会话搜索后本地合并。该方案需要按会话维持独立游标，会话数量较多时请求量和限流风险显著上升，跨会话稳定排序也更复杂。
2. 本地全文索引。该方案需要预先同步大量聊天历史，增加首次同步时间、磁盘占用和隐私风险，与当前下载器按需搜索资源的定位不符。

服务端全局搜索只传递关键词、日期边界、分页参数和 Telegram 媒体筛选所需信息。应用继续在本地执行现有媒体类型识别、相册补齐、结果数量控制和下载去重。

## 界面与交互

### 搜索范围入口

- 在现有会话列表顶部加入虚拟入口“全部会话”，页面打开且账号在线时默认选中。
- “全部会话”不写入 `dialogs` 表，也不伪装成真实 Telegram 会话。
- 选择“全部会话”时，页面标题和搜索记录范围均显示“全部会话”。
- 选择某个真实群组或频道时继续使用现有单会话搜索流程。
- 会话名称筛选只过滤真实会话；“全部会话”入口始终保留在列表顶部。

### 结果列表

- 搜索结果表增加“来源”列，显示来源名称，并在工具提示中显示来源类型和稳定 `peer_ref`。
- 来源类型至少区分群组、频道、私聊、机器人和收藏夹。来源类型只用于展示与测试，不参与媒体唯一性判断。
- 结果继续显示预览、日期、摘要、媒体类型、大小、选择状态和入队状态。
- 首批和每次“加载更多”最多新增 100 个媒体结果。后台可以读取多个 Telegram 结果页，以跳过纯文本或不符合媒体类型的消息。
- 全账号结果按 `(消息时间倒序, peer_ref, 消息 ID 倒序, media_id)` 稳定排序，避免不同会话中相同消息 ID 造成不稳定顺序。
- 全账号合计结果达到用户上限后结束搜索；不会继续为每个会话追加同等数量。

### 历史与恢复

- 搜索历史明确记录 `single_dialog` 或 `all_dialogs` 范围。
- 同一账号、搜索范围、规范化关键词和筛选条件对应一条可原位刷新的历史记录。
- 重启后可查看已保存结果和选择状态。全局复合游标持久化后，“加载更多”可以从安全位置继续；主动“重新搜索”仍创建新代次并从头刷新。

## 领域模型

新增 `SearchScope`：

- `SINGLE_DIALOG`：现有单会话搜索。
- `ALL_DIALOGS`：当前账号全部可访问云端会话。

扩展 `SearchCursor`，使其可表达两种分页状态：

- 单会话：`offset_id`。
- 全账号：`offset_rate`、`offset_peer_ref`、`offset_id`。

全账号游标对应 Telegram `messages.searchGlobal` 的分页三元组。`offset_peer_ref` 保存稳定 peer ID；发起下一页请求时由网关重新解析为 `InputPeer`，不把 Telethon 对象或访问哈希写进目录数据库。游标采用带版本号的 JSON 表示，以便以后兼容 Telegram 或 Telethon 的分页字段变化。

扩展 `SearchResult`：

- `source_title`：产生该媒体的真实会话名称。
- `source_kind`：群组、频道、私聊、机器人或收藏夹。

扩展任务来源类型，增加账号级搜索来源。任务本身的来源显示为“全部会话”，每个媒体仍保留真实 `peer_ref`，目标归档目录使用各自结果的 `source_title`。

## Telegram 网关

在 `TelegramGateway` 协议中新增账号级分页方法，保持单会话方法不变：

```text
search_all_media_page(query, cursor, on_progress) -> RemoteSearchPage
```

`TelethonGateway` 使用原始 `messages.SearchGlobalRequest`，原因是全局分页必须读取响应的 `next_rate`，并同时保存最后一条消息的来源 peer 和消息 ID。仅重新调用 `iter_messages(None, offset_id=...)` 无法完整表达跨会话分页位置。

每次 Telegram 请求最多读取 100 条服务端命中消息：

1. 使用查询日期边界和当前复合游标请求一页。
2. 根据响应中的 `users`、`chats` 和消息 `peer_id` 解析稳定 `peer_ref`、来源名称与来源类型。
3. 初始化 Telethon 消息实体上下文后，复用现有媒体识别和安全摘要逻辑。
4. 跳过纯文本消息和未选媒体类型，但计入“已扫描”进度。
5. 以响应 `next_rate` 和最后一条有效服务端消息构造下一页游标。
6. 响应为空、没有后续页或到达日期下限时标记耗尽。

全局搜索由 Telegram 决定哪些当前账号云端会话可搜索，因此自然包含已归档会话。秘密聊天不在 Telegram 云端 API 搜索结果中。

## 内容浏览服务

`ContentBrowserService.start_search()` 接收显式搜索范围：

- `SINGLE_DIALOG`：验证真实会话可用性，并调用现有 `search_media_page()`。
- `ALL_DIALOGS`：不读取虚拟会话实体，调用 `search_all_media_page()`。

服务继续负责分页填充、相册补齐、结果限制、选择持久化和队列准备。跨会话模式需要以下调整：

- 相册键从单独的 `grouped_id` 改为 `(peer_ref, grouped_id)`，因为不同会话可能出现相同相册 ID。
- 相册补齐继续按媒体真实 `peer_ref` 调用 `expand_album()`；补齐成员继承同一来源名称和类型。
- 媒体唯一键仍为 `(peer_ref, message_id, media_id)`。
- 每次用户操作最多新增 100 个结果；当一个 Telegram 页没有足够媒体时，服务继续读取下一页，直到填满本批、全账号上限已满、搜索耗尽、取消或发生错误。
- 为避免异常响应导致无限循环，服务拒绝与当前游标完全相同的下一页游标，并把搜索标记为不完整。
- 相册作为完整单元计入限制；若剩余名额不足以容纳整个相册，则不保存半个相册，并从安全游标继续处理后续内容。

## 目录数据库迁移

`catalog.sqlite3` 增加下一版本迁移，保留现有账号、会话、搜索历史、结果、选择状态和订阅数据。

`search_sessions` 增加：

- `scope`：默认 `single_dialog`，使既有记录自动保持原语义。
- `cursor_json`：保存版本化复合游标；既有 `next_offset_id` 在读取旧记录时转换为单会话游标，迁移稳定后可保留为兼容字段。

全账号记录使用仅存在于 `search_sessions` 的保留范围键，不向 `dialogs` 表插入虚拟记录。搜索唯一性包含账号、范围、真实会话或全账号范围键、规范化关键词和筛选指纹。

`search_results` 增加：

- `source_title`：既有单会话结果由对应搜索记录的 `dialog_title` 回填。
- `source_kind`：既有结果根据 `dialogs` 表回填；无法确定时使用安全的 `unknown` 展示值，不影响下载。

保存结果时：

- 单会话搜索仍校验所有结果与搜索会话 `peer_ref` 一致。
- 全账号搜索允许多个 `peer_ref`，但必须属于当前账号发起的同一搜索代次。
- 所有读取继续显式限定 `account_id`，避免跨账号历史混合。

迁移在单一 SQLite 事务中完成。迁移失败时保持旧数据库可恢复，不修改 `tasks.sqlite3`。

## 下载队列与文件归档

- 全账号搜索的一次选择创建一个下载任务，任务标题为“全部会话（搜索：关键词）”。
- 任务来源引用使用账号级搜索标识，不伪造 Telegram 链接。
- `TaskPlanner` 构建目标路径时使用每个 `RemoteMedia.source_title`，而不是统一使用任务级“全部会话”。现有单会话、链接扫描和自动订阅中的每项来源标题相同，因此行为保持不变。
- 每个 `MediaItem` 继续保存真实 `peer_ref`，下载和媒体引用刷新仍能定位原消息。
- 提交前和数据库事务内继续按 `(peer_ref, message_id, media_id)` 双重去重。
- 一个来源失权、消息删除或引用过期只影响对应媒体，不影响任务内其他来源的媒体。

## 数据流

1. 账号内容页面加载缓存会话，并在列表顶部展示“全部会话”。
2. 用户使用默认全账号范围提交关键词和筛选条件。
3. 控制器创建 `ALL_DIALOGS` 搜索查询；目录仓库创建或刷新搜索代次。
4. 内容浏览服务调用全局网关页，解析来源、过滤媒体并按真实 peer 补齐相册。
5. 服务进行跨会话去重和稳定排序，批量保存结果、来源字段与下一页复合游标。
6. 界面显示首批结果和来源；用户可继续加载、预览和选择。
7. 用户加入队列时，服务重新检查可用性与重复状态，计划器按每项真实来源生成目标路径。
8. 下载器继续按媒体真实 peer 和消息 ID 下载，任务中心显示一个账号级搜索任务。

## 并发、取消与性能

- 继续使用账号级前台搜索锁；全账号搜索与单会话搜索不能同时运行。
- 用户取消、切换账号或应用退出时取消当前全局请求与后续相册补齐任务。
- 取消或临时错误前已经成功保存的页面保留，搜索记录标记为“不完整”。
- 进度同时显示服务端已扫描消息数和已接受资源数，避免连续无媒体页时看似卡住。
- Telegram 限流继续转换为现有 `FloodWaitError`，界面显示安全等待秒数，不做高频自动重试。
- 单次数据库保存使用短事务；缩略图仍按可见行懒加载。
- 不预同步完整会话历史，不新增后台长期索引任务，也不增加按会话并发搜索风暴。

## 错误处理与隐私

- 未登录或离线：不能发起全账号搜索，但可查看已有历史。
- 会话或单条消息失权：对应结果标记不可用，其余结果保持可操作。
- 分页游标无法解析来源 peer：保留已有结果并标记搜索不完整，用户可重新搜索。
- 数据库迁移失败：账号内容功能进入安全错误状态，已有下载任务数据库不受影响。
- 来源名称经过现有路径组件清理；消息摘要继续限制长度并去除不可显示字符。
- 不在普通日志中记录关键词、消息全文、联系人完整资料、会话字符串、API Hash 或其他现有敏感信息。
- 本地只保存搜索条件、有限摘要、来源显示信息、结果元数据、缩略图和分页游标，不保存完整聊天记录。

## 测试与验收

### 自动化测试

1. 网关：全局请求参数、群组/频道/私聊/机器人/收藏夹来源解析、已归档结果、`next_rate` 复合游标、空页、日期边界、异常映射和进度。
2. 领域与仓库：搜索范围校验、游标 JSON 往返、旧单会话游标兼容、无损迁移、账号隔离、全账号搜索唯一性、结果来源字段和多 peer 结果保存。
3. 服务：首批与加载更多、跨会话稳定排序、`(peer_ref, grouped_id)` 相册隔离、全账号总上限、无媒体页续取、重复游标防护、取消和部分结果保留。
4. 界面：“全部会话”默认入口、真实会话筛选不隐藏虚拟入口、全局搜索信号、来源列、历史范围和离线状态。
5. 队列：一个任务包含多个 peer、每项按真实来源归档、跨会话去重、部分失效、全重复不建空任务和下载刷新定位正确。
6. 回归：现有单群组/频道搜索、相册、缩略图、链接下载、自动订阅、任务暂停恢复和全部原有测试继续通过。

### 人工验收

- 使用含群组、频道、联系人、机器人、收藏夹和归档会话的已登录账号进行关键词搜索。
- 不选择具体群组即可看到多个来源的媒体，来源名称和类型正确，结果总数不超过全账号上限。
- 连续“加载更多”无重复、无漏掉半个相册，重启后历史、来源和选择状态仍在。
- 从多个来源选择媒体后只创建一个任务，文件进入各自来源目录并能完成下载。
- 断网、取消和 Telegram 限流时保留已获得结果；恢复后可重新搜索，现有任务不受影响。

## 发布边界

规格确认后先形成实施计划，再按测试驱动方式实施并完成自动化与真实账号验证。是否提交功能代码、合并主分支、修改版本号、生成安装包、发布 GitHub Release、同步魔塔或切换在线更新指针，均需遵循后续明确授权。
