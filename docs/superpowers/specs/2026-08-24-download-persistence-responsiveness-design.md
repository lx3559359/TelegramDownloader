# 下载持久化响应优化设计

## 状态

已确认。本设计定义 v0.18.2 之后的下一轮下载响应优化；本轮只准备本地候选，不自动推送版本标签、公开安装包或在线更新指针。

## 背景与证据

v0.18.2 已将搜索结果模型、搜索目录操作、历史加载、选择保存、入队预检和缩略图目录查询移出 UI 事件循环。七次合成基准中，10,000 条搜索结果首次装载中位数为 10.65 ms，单行更新中位数为 8.34 ms，`UPDATE_SCALE_10000_OVER_2000` 为 5.40，说明搜索结果模型不再是当前主要瓶颈。

下载路径仍会从 `MediaDownloader` 和 `DownloadScheduler` 直接调用同步 `TaskRepository`。仓库方法每次打开 SQLite 连接并执行事务；下载进度、任务状态、重试状态和终态都可能占用 asyncio 事件循环。合成诊断将每次仓库写入固定延迟设为 50 ms，20 个连续数据块产生 22 次仓库调用，总耗时 1,147.84 ms，事件循环最大心跳间隔达到 63.00 ms。这个停顿足以让窗口操作、托盘菜单和下载控制产生可见卡顿。

## 目标

- 将下载进度、任务状态和重试状态的 SQLite 工作全部移出事件循环。
- 将同一媒体的高频进度更新按 500 ms 窗口合并，只保存窗口内最新值。
- 保证暂停、失败、完成和重试等状态不会被较早的进度更新覆盖。
- 保证暂停、失败和完成操作返回前，相应最新进度与终态已经落盘。
- 模拟每次数据库操作阻塞 50 ms 时，事件循环最大停顿不超过 20 ms。
- 20 次连续进度更新最多产生 4 次媒体进度持久化写入，包括开始状态、合并进度和终态。
- 保持现有数据库结构、任务数据、下载目录、`.part` 恢复规则和用户操作语义兼容。

## 非目标

- 不把整个应用的 `TaskRepository` 重写成异步数据库框架。
- 不引入 `aiosqlite` 或其他数据库依赖。
- 不改变全局媒体槽数量、带宽算法、文件写入批次或 Telegram 下载协议。
- 不修改搜索、订阅、维护中心或更新系统的数据模型。
- 不新增设置项或 UI 控件。
- 不在本轮自动执行正式在线发布。

## 总体架构

新增 `DownloadPersistenceCoordinator`，作为下载运行时与现有 `TaskRepository` 之间的唯一持久化边界。应用创建一个协调器实例，并将同一实例注入 `MediaDownloader` 与 `DownloadScheduler`。协调器归属 asyncio 事件循环，但实际仓库调用通过可注入的后台执行器运行；生产环境使用 `asyncio.to_thread`，测试可使用可控执行器。

协调器包含四类能力：

1. `record_progress`：事件循环内的常量时间内存更新。按媒体 ID 覆盖尚未提交的旧进度，并唤醒后台写入器；调用本身不等待 SQLite。
2. 有序仓库命令：任务状态、重试状态、终态和需要顺序一致性的读取进入一个命令通道，后台逐项执行并通过 future 返回结果。
3. 进度屏障：终态命令执行前先提交目标媒体尚未写入的最新进度；旧进度不能跨过屏障。
4. 生命周期：`drain` 刷新全部进度并等待命令完成，`close` 阻止新操作并结束后台写入器。

`TaskRepository` 保持同步接口与现有调用者兼容，但新增一个批量媒体进度事务。协调器一次把多个媒体的最新快照交给该方法，避免每个媒体分别打开连接和提交事务。下载之外的既有调用不强制迁移到协调器。

## 组件职责

### DownloadPersistenceCoordinator

- 维护待提交进度映射、下次 500 ms 截止时间、有序命令队列、后台工作任务和关闭状态。
- 进度快照包含媒体 ID、下载字节数、媒体状态、脱敏错误和重试次数。
- 对同一媒体只保留最后一个尚未提交的快照；不同媒体可进入同一批量事务。
- 屏障命令先提取并提交目标媒体的待处理快照，再执行终态操作。
- 普通有序命令按照入队顺序执行；需要读取刚写入状态的命令先经过全局进度屏障。
- 后台仓库操作失败后进入粘性故障状态，保存首个脱敏异常并拒绝后续操作。
- 提供内存级故障通知，使调度器立即关闭接纳并设置活动任务暂停标记。

### TaskRepository

- 新增批量进度更新方法，在一个连接和事务中更新多个不同媒体。
- 对重复媒体 ID 拒绝输入；协调器负责在调用前完成按 ID 合并。
- 保留现有单项更新、完成、任务汇总和恢复方法，避免数据库迁移。
- 批量事务中任何一项失败时整体回滚，不产生部分进度提交。

### MediaDownloader

- 不再直接执行同步进度和完成写入。
- 开始下载时通过有序命令写入 `DOWNLOADING` 并等待落盘。
- 下载过程中调用 `record_progress`，不等待数据库。
- 暂停、空间不足、取消和完成时使用媒体屏障，再写入对应终态。
- 文件批次写入、SHA-256 和 `.part` 耐久刷新继续使用现有后台文件 I/O 实现。

### DownloadScheduler

- 所有任务状态、重试状态、项目读取和任务汇总通过协调器的有序命令执行。
- 暂停标记、接纳开关、队列顺序和活动任务集合仍在事件循环内立即更新。
- 公开的暂停、恢复和选定媒体运行入口在需要持久化时改为可等待操作；控制器负责等待结果和刷新 UI。
- 协调器报告故障时立即停止接纳新任务，并为活动任务设置内存暂停标记。
- 调度器关闭完成后调用协调器 `drain`，确保进度和状态先落盘，再关闭协调器。

### 应用装配与生命周期

- 应用装配层为一个 `TaskRepository` 创建一个协调器，并共享给下载器和调度器。
- 协调器后台任务只在运行中的 asyncio 循环内启动，不在模块导入或同步构造阶段创建任务。
- 正常退出顺序为：停止接纳、暂停或完成活动下载、调度器关闭、协调器 `drain`、协调器 `close`、其余服务关闭。
- 测试装配可注入即时执行器、阻塞执行器和故障执行器，不增加生产代码中的测试专用分支。

## 数据流与顺序不变量

### 正常下载

1. 调度器通过有序命令把任务标记为下载中并读取待运行媒体。
2. 下载器通过有序命令把媒体标记为下载中。
3. 每次可见进度变化只更新协调器内存快照。
4. 后台写入器在 500 ms 截止时间到达时，将所有媒体的最新快照放进一次 SQLite 事务。
5. 下载完成时，媒体屏障先刷新该媒体的最后进度，再调用现有 `complete_item`。
6. 所有媒体结束后，调度器通过有序命令计算并写入任务终态。

### 暂停、取消和重试

- 用户暂停先设置内存暂停标记，因此网络读取和文件写入能立即观察到请求。
- 下载器耐久刷新 `.part` 后，通过媒体屏障提交最新字节数和暂停状态。
- 取消不能取消已经进入有序通道的终态命令；终态 future 使用取消保护。
- 网络重试先通过屏障写入最新进度与 `WAITING_RETRY`，再进入退避等待；重试开始前写回 `DOWNLOADING`。
- 同一媒体在一个活动下载操作中不会并发运行；现有调度器去重合同保持不变。

### 关键不变量

- 旧进度不能晚于暂停、失败或完成状态写入。
- 终态方法成功返回意味着相应终态已经提交到 SQLite。
- 批量进度只减少事务数量，不改变单个媒体的最新字节数。
- 协调器关闭后拒绝新进度和新命令。
- 强制终止最多损失不足 500 ms 的数据库进度；恢复仍以 `.part` 文件实际长度为准，因此不会覆盖已下载内容。

## 故障处理

后台批量进度或有序命令失败时，协调器记录首个脱敏异常并进入故障状态。故障处理只执行内存操作：关闭调度器接纳、设置活动任务暂停标记并触发现有下载失败提示。后续进度提交和有序命令立即得到同一故障，不允许继续积累未持久化状态。

SQLite 已配置 5 秒 busy timeout；协调器不额外无限重试。超时或其他仓库错误通过现有控制器错误边界展示，用户可在存储恢复后重试。若暂停状态本身无法写入，`.part` 文件仍先完成耐久刷新，下一次启动由现有 `recover_interrupted` 流程恢复任务。

所有错误文本经过现有安全错误转换，不记录目标路径、Telegram 链接、消息内容、账号凭据或数据库记录。

## 性能合同

- 人工让每次仓库操作阻塞 50 ms，下载期间运行 5 ms 心跳；最大事件循环间隔必须不超过 20 ms。
- 快速产生 20 次同一媒体进度时，包括开始、合并进度和终态在内的媒体持久化调用不超过 4 次。
- 五个媒体同时更新时，一个截止窗口只产生一次批量事务。
- 终态屏障必须立即刷新目标媒体，不额外等待剩余 500 ms。
- 合并不能延长文件写入、带宽限制或暂停检查的现有周期。

## 测试策略

### 单元测试

- 先写失败测试证明当前同步仓库调用会阻塞事件循环。
- 验证同一媒体 20 次进度只保留最新值并满足最多 4 次媒体持久化调用。
- 验证多个媒体在同一批量事务提交。
- 验证完成、失败、暂停和重试屏障严格排在旧进度之后。
- 验证终态 future 在仓库调用结束前不会完成。
- 验证批量事务失败整体回滚，协调器进入粘性故障并拒绝新工作。
- 验证取消保护、`drain`、`close` 和关闭后拒绝写入。

### 集成测试

- 使用真实临时 `TaskRepository` 验证批量进度、任务汇总和重启读取。
- 扩展真实队列端到端测试，覆盖暂停、继续、优先级交接、完成和 `.part` 恢复。
- 验证调度器故障时关闭接纳并暂停活动任务。
- 验证应用装配只创建一个共享协调器，退出顺序先于剩余运行时关闭。

### 合成基准与隐私

新增纯合成下载持久化基准，只使用临时目录、固定媒体 ID、固定字节块和人工仓库延迟。脚本不得打开应用数据目录、真实任务数据库、下载目录、账号会话或网络连接；打包合同测试扫描脚本，防止引入真实数据路径或凭据字段。

## 三轮验收

1. 运行聚焦测试、完整 Pytest、Ruff 和七次合成性能基准；必须满足 20 ms 心跳与最多 4 次媒体持久化调用。
2. 构建便携包，要求构建内测试、Ruff 和 `PACKAGED_SMOKE_OK` 通过。
3. 构建安装器并执行非系统盘安装、升级、卸载数据保留、冻结自检和合成 GUI 响应检查，要求 `INSTALLER_SMOKE_OK` 通过。

## 发布边界

本设计、实现、测试和三轮构建只形成下一版本的本地候选。只有在用户再次明确要求“合并并发布更新”后，才允许合并到 `main`、创建标签、上传 GitHub/ModelScope 资产或修改 stable 指针。
