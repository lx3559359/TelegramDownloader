# 自动订阅下载设计

## 背景与目标

TelegramDownloader 已支持账号群组同步、群内关键词搜索、选择性入队、任务去重、断点续传和失败恢复，但每次发现新内容仍需要用户手动打开群组、搜索并选择结果。

本功能把已有搜索与下载能力扩展为应用内增量订阅：用户为已加入的群组或频道创建规则，程序运行期间按间隔检查新消息，把符合条件的新媒体自动加入现有下载队列。所有规则、游标、运行记录、缓存和下载继续保存在应用目录，不使用 Windows 计划任务、系统服务、注册表或系统临时目录保存业务数据。

成功标准：

- 用户可以创建、编辑、暂停、继续、立即检查和删除订阅规则。
- 首次启用规则只建立增量基线，默认不下载历史消息。
- 后续检查只处理基线之后的新消息，并准确过滤关键词和媒体类型。
- 同一媒体在重复扫描、程序重启、相册展开或规则重叠时不会重复创建下载任务。
- 断网、Telegram 限流、登录失效和应用退出不会损坏规则或越过未完成消息。
- 自动检查不会让手动同步、搜索、预览和下载界面失去响应。

## 方案选择

采用应用内增量调度方案。程序启动后恢复到期规则，运行期间由异步调度器执行，退出后停止。该方案与现有 qasync、Telethon 网关和项目内数据边界一致，开发与运行风险最低。

不采用以下方案：

- Windows 计划任务：能够在主程序关闭时运行，但会产生系统级任务状态并扩大安装、权限和系统盘数据边界。
- Windows 后台服务或开机常驻：自动化程度更高，但需要独立进程、服务权限、进程间通信和额外升级协议，不适合作为本次增量功能的第一版。

## 用户体验

主窗口新增“自动订阅”页面，页面包含规则列表、状态摘要和规则编辑区。

每条规则包含：

- 当前账号和一个已加入、当前可用的群组或频道。
- 一个必填关键词。一个规则只负责一个关键词；多个关键词通过创建多条规则实现。
- 至少一种媒体类型：图片、视频、音频、语音、文档或压缩包。
- 检查间隔：5、15、30、60 或 180 分钟，默认 30 分钟。
- 启用状态、上次检查时间、下次检查时间、最近结果和最近错误。

页面操作：

- “新建订阅”打开规则编辑对话框。
- “立即检查”让选中规则在当前前台操作完成后尽快运行。
- “暂停/继续”只改变后续自动检查，不影响已经进入下载队列的任务。
- “编辑”修改关键词、媒体类型或间隔；群组或关键词改变时重新建立基线，避免把另一条消息流误认为旧游标的延续。
- “删除”只删除规则和运行记录，不删除已创建任务或已下载文件。

规则状态包括“正在建立基线”“等待检查”“检查中”“已暂停”“等待网络”“需要重新登录”和“检查失败”。运行时显示扫描消息数、匹配媒体数、新增任务数、重复数和下次检查时间。所有按钮在动作开始后立即显示忙碌反馈，并阻止同一动作重复提交。

## 首次启用与增量语义

新规则保存后先读取目标会话当前最新消息 ID，把它保存为基线。基线建立成功前不会执行自动下载。这样默认只订阅启用之后的新内容，不会意外抓取整个历史。

Telegram 消息 ID 在同一会话内单调增加。每次检查先固定本轮可见的最新消息 ID，然后按从旧到新处理 `(last_message_id, snapshot_message_id]` 区间。每条消息中的媒体完成以下任一确定性结果后，才把规则游标推进到该消息：

- 成功创建任务；
- 已存在相同任务；
- 不符合规则；
- 消息没有可下载媒体；
- 媒体被平台永久标记为不可用。

网络异常、限流、登录失效或未知异常不会越过当前未完成消息。下次运行从最后已提交游标继续。相册通过现有 grouped media 展开能力补齐，并使用 Telegram 会话、消息和媒体标识进行数据库级去重。

单次规则最多检查 500 条新消息。仍有积压时保存安全游标并在短暂让出前台后继续，不把一次长时间离线变成阻塞界面的超长操作。

## 架构与组件

### 订阅领域模型

新增独立 `subscriptions.py`，定义 `SubscriptionRule`、`SubscriptionRun`、规则状态、运行摘要和校验逻辑。领域模型不依赖 Qt、SQLite 或 Telethon。

### 目录数据库

`CatalogRepository` 从 schema v1 幂等迁移到 v2，新增：

- `subscription_rules`：账号、会话、关键词、媒体类型、间隔、启用状态、增量游标、到期时间、最近错误和时间戳。
- `subscription_runs`：规则、开始/结束时间、扫描数、匹配数、新增数、重复数、结果状态和脱敏错误。

规则按账号隔离；外键删除只清理规则运行记录，不触碰任务数据库或下载文件。运行记录每条规则最多保留最近 100 次，避免数据库无限增长。

### Telegram 增量读取

`TelegramGateway` 增加两个窄接口：读取会话最新消息 ID，以及读取指定 ID 区间内的一页消息。网关只负责 Telegram 访问和媒体元数据转换，不负责持久化、入队或调度策略。

### 订阅服务

`SubscriptionService` 负责：

- 创建和编辑规则时建立基线；
- 读取增量消息并应用关键词、媒体类型和相册规则；
- 复用 `TaskPlanner` 的任务创建与数据库去重能力；
- 按消息提交游标和运行摘要；
- 对外发送进度事件。

自动订阅不创建普通手动搜索历史，也不默认下载缩略图，避免污染用户的搜索结果页和产生无用缓存。

### 异步调度器

`SubscriptionScheduler` 在现有 qasync 事件循环中运行，最多同时执行一条订阅规则。它支持启动恢复、规则变更唤醒、立即检查、网络恢复和安全关闭。

手动群组同步、手动搜索、登录操作拥有前台优先级。自动订阅以小分页运行并主动让出事件循环；检测到前台 Telegram 操作时延后本轮，不与用户动作争抢连接。下载任务仍由现有 `DownloadScheduler` 控制，订阅功能只负责创建任务。

### 控制器与界面

`AppController` 负责把当前账号、连接状态、规则服务和新页面连接起来。新增 `ui/subscriptions.py`，保持规则表格、编辑对话框和忙碌态只处理展示与信号，不直接访问数据库或 Telegram。

登出或切换账号时停止当前账号的调度任务，但保留其规则。重新登录同一账号后恢复；登录其他账号时只展示和运行新账号自己的规则。

## 调度与退避

成功完成后，`next_run_at = finished_at + interval`。程序启动时只执行已经到期的规则，不为关闭期间的每个间隔补跑多次；一次增量检查会覆盖游标之后的全部新消息。

失败处理：

- 暂时断网或代理不可用：保留游标，以 1、2、5、15 分钟递增退避，网络恢复后允许立即唤醒。
- Telegram FloodWait：严格使用平台给出的等待时间，并在界面显示可读的恢复时间。
- 登录失效：规则进入“需要重新登录”，不自动清除加密会话或规则；重新登录后恢复。
- 群组已退出或不可用：暂停该规则并显示原因，用户刷新群组后可以重试。
- 单条永久不可下载媒体：记录跳过原因并继续，不让整条规则永久卡住。
- 未知异常：保留未完成消息前的游标，记录脱敏错误并按失败退避重试。

一个规则失败不会停止其他规则。日志不得包含 API Hash、Session、代理密码、二维码令牌、完整手机号或完整消息正文。

## 数据与磁盘边界

新增代码只使用现有 `ApplicationPaths` 提供的应用目录路径。数据库继续位于 `data/database`，日志位于 `data/logs`，下载位于 `downloads`。不使用 `%APPDATA%`、`%LOCALAPPDATA%`、系统 `%TEMP%`、Windows 服务或计划任务保存订阅状态。

规则不会绕过 Telegram 权限、内容保护或已删除状态，只处理当前登录账号正常可查看的消息。

## 测试与验收

自动化测试覆盖：

- catalog v1 到 v2 迁移、账号隔离、规则 CRUD、游标原子推进和运行记录裁剪；
- 首次启用仅建立基线，不创建历史任务；
- 增量消息过滤、顺序处理、相册展开、规则重叠和重复任务；
- 中途网络失败不越过消息，重启后从安全游标继续；
- 断网退避、FloodWait、登录失效、不可用群组和立即检查；
- 前台优先、重复动作抑制、关闭时任务取消与等待；
- 规则页面校验、按钮忙碌态、账号切换和运行进度；
- 所有新增文件路径仍位于项目/应用目录。

完成后运行完整 pytest、Ruff、便携包自检和安装包构建/自检。真人式检查使用现有项目内会话完成群组同步、创建规则、建立基线、立即检查、暂停恢复和重启恢复；不为验证而删除现有会话、任务或下载文件，也不把用户数据打入发布包。

本次范围不包含跨群组全局搜索、Windows 后台服务、开机启动、历史补抓、复杂布尔关键词、带宽限速和外部通知。这些能力可以在订阅基础稳定后单独设计。
