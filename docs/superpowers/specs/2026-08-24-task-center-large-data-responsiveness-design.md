# TG 快取任务中心大数据响应优化设计

日期：2026-08-24

状态：已确认设计，等待用户复核书面规格

目标版本：v0.18.4 本地候选

基线提交：`4e13151`（v0.18.3 下载持久化响应本地候选）

## 1. 背景

v0.18.2 已把 10,000 条账号内容搜索结果的首次装载和单行更新降到约 12 ms 与 9 ms；v0.18.3 已把下载进度、任务状态和终态 SQLite 操作移出事件循环，并在固定 500 ms 窗口内合并进度写入。任务中心仍有四个随数据量线性增长的界面路径：

- `Controller.start()` 启动时同步读取并转换全部任务快照。
- 500 ms 进度刷新会重新读取并转换全部任务快照，即使只有一个任务变化。
- 任务名称每次 `textChanged` 都立即筛选、重置模型并重复遍历各状态计数。
- 选择一个任务时同步读取该任务全部媒体，媒体模型每次都执行完整重置。

这些路径在普通数据量下可接受，但大量单文件任务或单任务含数万媒体时会造成输入迟滞、选择闪动、滚动位置丢失和事件循环停顿。本设计只优化任务中心的数据读取、模型更新、筛选和媒体明细加载，不改变账号内容搜索、下载协议、下载调度、订阅规则或在线更新语义。

## 2. 目标与非目标

### 2.1 目标

- 10,000 个任务时，首次装载、筛选切换和单行更新的七次中位数均不超过 100 ms。
- 单任务 50,000 个媒体项时，首批 500 条在 100 ms 内显示；后续分页期间 Qt 事件循环最大间隔不超过 20 ms。
- 下载进度继续约每 500 ms 更新；暂停、失败、完成、新建、删除、归档、恢复和优先级变化立即反映。
- 常规刷新不重置任务模型或媒体模型，并保留选中项、当前行和滚动位置。
- 数据库快照继续作为最终事实来源；增量提示丢失时最多 5 秒完成自动校准。
- 不读取或记录真实账号、消息、任务名称、文件名、路径或凭据作为性能验证数据。

### 2.2 非目标

- 不改变 Telegram 搜索并发、FloodWait 恢复或云端分页。
- 不改变媒体槽、带宽限制、文件批量写入或下载持久化的 500 ms 固定窗口。
- 不增加任务或媒体业务字段，不重写现有任务数据库。
- 不在本设计阶段合并主分支、打标签、上传制品或推进在线更新指针。

## 3. 方案选择

采用“事件增量 + 定期完整校准 + 媒体虚拟分页”的混合方案。

纯界面增量方案改动较小，但仍会每 500 ms 全量读取和转换所有任务。完全数据库分页方案扩展性最高，却会显著扩大任务筛选、实时进度和选择恢复的改造面。混合方案让日常刷新成本与实际变化量相关，同时用周期性完整快照维持最终一致性，适合当前架构和风险边界。

## 4. 架构

### 4.1 `TaskRefreshCoordinator`

新增独立协调器，负责任务中心的刷新节奏和代次，不负责下载或数据库写入。它由控制器拥有，使用现有 asyncio/qasync 事件循环，并通过后台线程执行仓库查询。

协调器维护：

- `dirty_task_ids`：待增量读取的任务 ID 集合。
- `immediate_task_ids`：终态和用户动作产生、需要立即刷新的任务 ID 集合。
- `progress_deadline`：固定 500 ms 的进度刷新截止时间；新事件不能延后已开始窗口。
- `reconcile_deadline`：任务中心可见期间每 5 秒一次完整校准。
- `refresh_generation`：账号服务替换或关闭时递增，旧查询结果只能被安全丢弃。
- `detail_generation`：选择任务改变时递增，旧媒体页不能覆盖当前任务。
- 单一刷新任务与 pending 标记：同类刷新并发时合并，不建立无界后台任务。

任务中心隐藏时停止 5 秒完整校准，不为不可见页面持续查询；再次进入时立即执行完整校准。下载调度继续独立运行。关闭应用时停止计时器并取消等待方；已经进入后台线程的 SQLite 查询允许结束，但其结果因代次不匹配而被丢弃。

### 4.2 仓库读取接口

`TaskRepository` 增加只读批量和分页接口：

```python
def list_task_snapshots_by_ids(
    self,
    task_ids: Collection[str],
    *,
    include_archived: bool = True,
) -> list[TaskSnapshot]: ...

def list_items_page(
    self,
    task_id: str,
    *,
    after: ItemPageCursor | None = None,
    limit: int = 500,
) -> ItemPage: ...

def get_items(self, item_ids: Collection[str]) -> list[MediaItem]: ...
```

批量任务快照在一个连接中按最多 200 个 ID 分块，避免 SQLite 参数上限，不执行逐任务查询。返回顺序固定为 `created_at DESC, id ASC`。

媒体页采用键集游标 `(message_date_utc, message_id, id)`，排序固定为 `message_date_utc DESC, message_id DESC, id ASC`。游标条件严格排除上一页末项，保证没有重复或遗漏；不使用后页越来越慢的 `OFFSET`。`ItemPage` 包含本页媒体、下一游标和任务媒体总数。

为分页增加幂等兼容索引：

```sql
CREATE INDEX IF NOT EXISTS idx_items_task_page
ON media_items(task_id, message_date_utc DESC, message_id DESC, id ASC);
```

索引不修改业务数据和 schema 版本。生产启动在主窗口可见后、恢复下载队列前通过后台线程创建索引：窗口保持可交互，下载恢复等待该一次性准备结束，避免索引构建与下载写入竞争。数据库繁忙或创建失败时保留现有查询能力；只有调度器空闲时才延后重试，不能在下载期间反复争用写锁。升级、原位安装和普通卸载继续保留原数据库。

### 4.3 任务视图索引

完整快照首次返回后建立以稳定任务 ID 为键的内存视图索引，并保留当前展示顺序。任务摘要构造在后台完成，只有不可变结果列表回到 Qt 线程。

增量刷新流程：

1. 用户动作和下载状态通知把任务 ID 放入 dirty 集合。
2. 普通进度按固定 500 ms 合并；终态、新建、删除、归档、恢复和优先级变化立即触发。
3. 协调器一次批量读取所有 dirty ID，并结合调度器的内存快照生成新摘要。
4. 模型按 ID 比较旧值和新值，只应用实际变化。
5. 每 5 秒完整校准任务集合、顺序和聚合值，修复漏事件。

若当前任务正在下载，500 ms 刷新同时更新已加载且当前可见的媒体 ID，以及仍被选中的媒体 ID。未加载或不可见媒体不创建 Qt 对象；它们在进入可见范围或重新加载页面时从数据库获取最新状态。

### 4.4 Qt 任务模型

`TaskTableModel` 维护 `task_id -> row` 映射和每个标题的预计算 `casefold` 值。

- ID 顺序不变时，把相邻变化行合并为最小 `dataChanged` 范围。
- 新建、删除和简单顺序变化分别使用 `beginInsertRows`、`beginRemoveRows` 和行移动信号。
- 复杂重排使用布局变化信号并按稳定 ID 恢复持久索引；常规路径不调用 `beginResetModel`。
- 只有检测到重复 ID 或内部索引损坏时才安全重建模型，并记录不含业务内容的诊断类型。
- 筛选一次遍历同时生成可见任务和所有状态计数，不再为每个筛选状态重复扫描。

任务列表更新后，窗口按任务 ID 恢复多选、当前行和滚动锚点。若当前任务因筛选条件消失，选择最接近原位置的可见任务；没有可见任务时清空明细并显示空状态。

### 4.5 筛选输入

任务名称输入使用 150 ms 单次计时器防抖：

- 普通键入重新启动计时器。
- Enter、点击清除和切换状态筛选会停止计时器并立即应用。
- 相同规范化文本与状态不重复刷新。
- 空格裁剪和大小写不敏感语义保持不变。

防抖只影响本地任务名称筛选，不改变账号内容搜索框。

### 4.6 媒体虚拟分页模型

`TaskItemTableModel` 支持增量首批、追加页和按媒体 ID 更新：

- 选择单个任务后立即显示加载状态，后台读取第一页 500 条。
- 当视图进入距离已加载末尾 100 行以内时预取下一页。
- 同一任务同一时刻最多有一个分页请求；重复滚动只合并为一次请求。
- 每页使用 `beginInsertRows` 追加，不重置已加载行。
- 已加载媒体以 `item_id -> row` 索引更新；相邻变化行合并发出 `dataChanged`。
- 页面标题显示“已加载 X / 共 Y 项”；全部加载后停止预取。
- 切换任务、账号服务替换或窗口关闭会递增代次，旧页结果不能写入新模型。

已加载行的选择按媒体 ID 保留。因为未加载媒体没有 Qt 行，所以批量动作只作用于用户实际选中的已加载媒体；整任务校验继续走已有“校验任务”入口，不依赖把 50,000 行全部装入界面。

## 5. 数据流时序

### 5.1 首次进入任务中心

1. 主窗口先保持可交互，控制器启动异步完整校准。
2. 仓库在线程中读取完整任务快照，摘要转换也在线程中执行。
3. Qt 线程一次建立任务视图索引并应用当前筛选。
4. 如果恢复了一个有效选中任务，启动对应媒体第一页请求。

GUI 启动路径不再调用同步 `refresh_tasks()`；同步入口只为无事件循环测试兼容保留，并不得由生产启动或 Qt 信号调用。

### 5.2 下载进度

1. 调度器活动任务 ID 或任务事件进入 dirty 集合。
2. 第一个普通进度建立 500 ms 截止时间，后续进度不延期。
3. 截止时一次批量读取 dirty 任务快照。
4. 如果 dirty 集合包含当前选中任务，再批量读取其可见和已选媒体 ID。
5. 模型只更新变化行。

### 5.3 用户动作与终态

暂停、继续、重试、归档、恢复、优先级调整和完整性操作在原仓库动作耐久完成后，把受影响 ID 放入立即队列并等待界面增量刷新。完成、失败和磁盘不足等终态同样立即刷新，不等待下一个 500 ms 窗口。新建任务在稳定 ID 已知后插入；删除或归档后若当前选择失效，按原行位置选择最近可见任务。

### 5.4 完整校准

任务中心可见时每 5 秒在后台读取完整快照。协调器按 ID 对比：

- 新 ID 插入。
- 缺失 ID 删除。
- 内容变化局部更新。
- 排序变化移动行或发出布局变化。

校准期间到达的新 dirty 事件保留到下一增量轮，不会被旧完整快照清除。应用完整结果前再次检查账号和刷新代次。

## 6. 错误处理与降级

- 增量查询失败：保留当前界面，不清空模型；显示脱敏状态信息，并由下一轮完整校准重试。
- 完整校准失败：保留最后成功快照，继续下载和用户操作；后续 5 秒周期重试。
- 媒体分页失败：保留已加载行，在底部显示“重试加载”，不遮挡现有内容。
- 索引创建失败或数据库繁忙：记录脱敏类别并延后重试；分页接口仍用兼容 SQL 返回正确结果。
- 旧代次完成：正常取回后台任务结果，但不更新模型，也不弹出错误。
- 模型输入出现重复 ID：拒绝局部应用，执行一次安全全量重建；不保留半更新状态。
- 协调器关闭：拒绝新刷新，等待已进入线程的只读查询结束并丢弃结果，不延长下载持久化关闭边界。

任何日志和诊断只记录动作类型、数量、耗时、代次和错误类别，不记录任务标题、来源、文件名、消息、路径或账号。

## 7. 性能与测试设计

### 7.1 仓库测试

- 批量任务快照为空、重复 ID、200 ID 分块、顺序和缺失任务合同。
- 50,000 条真实临时 SQLite 媒体的键集分页：页间无重复、无遗漏、顺序稳定。
- 同时间和同消息 ID 的媒体以 `id ASC` 正确续页。
- 分页索引可幂等创建，不改变业务数据和 schema 版本。
- 查询计数证明增量刷新不产生 N+1。

### 7.2 协调器测试

- 500 次连续进度提示在固定窗口内只形成一次 dirty 批次；新提示不能推迟截止时间。
- 终态和用户动作绕过普通窗口并等待界面刷新。
- 5 秒完整校准修复漏事件。
- 页面隐藏停止周期校准，重新进入立即校准。
- 账号、任务和媒体代次隔离；取消等待方不能留下未取回异常。
- 50 ms 人工慢仓库期间 5 ms 事件循环心跳持续推进。

### 7.3 Qt 模型与交互测试

- 10,000 个任务的单行更新、插入、删除、移动和筛选不发出 `modelReset`。
- 150 ms 防抖只应用最后输入；Enter、清除和状态切换立即应用。
- 筛选计数一次遍历得到正确结果。
- 多选、当前行、滚动锚点和复杂重排后的稳定 ID 保持。
- 50,000 个媒体首次只建立 500 行；接近末尾追加下一页；重复请求合并。
- 分页失败保留现有行并可重试；切换任务丢弃旧页。
- 已加载媒体局部进度更新不重置模型。

### 7.4 性能基准

新增只使用固定合成任务、临时 SQLite 和离屏 Qt 的独立基准：

- 10,000 个任务：首次装载、筛选切换和单行更新各运行七次并取中位数，目标均不超过 100 ms。
- 50,000 个媒体：第一页 500 条七次中位数不超过 100 ms。
- 50 ms 人工仓库延迟下，分页和任务增量刷新期间 Qt 最大心跳间隔不超过 20 ms。
- 500 个进度提示的任务快照批次数符合固定窗口和 dirty 去重合同。

绝对时间记录在验证文档；持续集成使用结构合同、查询次数、模型信号范围和事件循环心跳作为稳定硬门禁。

### 7.5 三轮最终自检

1. 聚焦测试、完整 Pytest、Ruff、七次任务与媒体性能基准。
2. 便携包构建、隐私扫描、冻结程序自检，以及 10,000/50,000 合成数据 Qt 冒烟。
3. 安装器、原位升级/普通卸载数据保留和隔离 GUI 人工检查。

三轮都要记录实际命令、测试数量、耗时、模型信号、查询次数、基准数值、制品大小和 SHA-256；未人工执行的项目必须明确记录，不得推测为通过。

## 8. 兼容性与发布边界

- 现有任务、媒体、进度、完整性、归档、优先级和下载路径数据保持不变。
- 只新增可删除重建的 SQLite 索引，不增加业务字段或迁移用户数据。
- 任务操作、媒体操作、筛选文本和排序语义保持现有行为。
- 账号内容搜索和下载持久化继续使用 v0.18.2/v0.18.3 已验证实现。
- 本工作只形成 v0.18.4 本地候选；没有新的明确授权时，不合并 `main`、不打标签、不推送、不上传制品、不修改 GitHub 或魔搭 stable 指针。
