# TelegramDownloader 扫码优先登录设计

日期：2026-08-13  
状态：待用户书面复核  
目标版本：v0.2.0

## 1. 目标

把当前手机号验证码向导改为“扫码优先”的登录体验：用户只在首次使用时填写自己的 Telegram API ID、API Hash 和可选代理；保存后显示二维码，使用已登录的 Telegram App 扫码授权。以后本地会话失效或用户主动重新登录时，程序直接进入扫码页。手机号、验证码和可选两步验证流程继续作为备用入口。

Telegram 的 QR 授权只替代手机号和验证码交互，不能替代 MTProto 客户端本身所需的 API ID/API Hash。程序不内置或共享公共 API 凭据。参考：

- Telegram QR 登录协议：https://core.telegram.org/api/qr-login
- Telegram API 凭据：https://core.telegram.org/api/obtaining_api_id
- Telethon `qr_login()` / `QRLogin.wait()`：https://docs.telethon.dev/en/stable/modules/client.html

## 2. 用户体验

### 2.1 首次使用

1. 登录向导显示“首次配置”。
2. 用户填写 API ID、API Hash，并可配置“不使用代理”、SOCKS5 或 HTTP 代理。
3. 点击“保存并生成二维码”后，程序验证字段、创建 Telegram 连接并将 API Hash、代理密码通过 Windows DPAPI 加密保存到应用目录。
4. 连接成功后切换到二维码页；不再要求用户先输入手机号。
5. 页面提示：Telegram App → 设置 → 设备 → 连接桌面设备。
6. 用户扫码并在手机端确认后，程序自动导出 StringSession、加密保存、刷新账号状态并关闭向导。
7. 若 Telegram 要求两步验证，二维码页切换到密码页；密码只用于本次授权，不保存到磁盘。

### 2.2 后续登录

- 已有有效 StringSession：应用直接恢复登录，不显示向导。
- 已保存 API 凭据但没有有效会话：点击“账号登录”直接进入二维码页并自动生成二维码。
- 扫码页始终提供“改用手机号登录”和“修改 API/代理设置”。
- 手机号备用流程沿用：手机号 → 验证码 → 可选两步验证 → 保存 StringSession。

### 2.3 二维码状态

- 显示清晰二维码、过期倒计时和当前状态：正在连接、等待扫码、手机确认中、已过期、登录成功或失败。
- 二维码过期后自动创建新令牌；同时提供“刷新二维码”按钮。
- 同一时刻只允许一个 QR 等待任务。手动刷新会先取消旧任务，再创建新任务。
- 关闭向导、切换到手机号方式、修改凭据或退出程序时，必须取消 QR 等待和自动刷新任务。
- 网络中断时显示脱敏中文错误，并允许重试；不记录二维码 URL、令牌、API Hash、2FA 密码或完整手机号。

## 3. 界面结构

现有 `LoginDialog` 保留单向导结构，页面调整为：

1. `CREDENTIALS`：首次 API/代理配置。
2. `QR`：默认登录页，包含二维码、倒计时、刷新按钮、备用手机号入口和修改设置入口。
3. `PHONE`：备用手机号输入。
4. `CODE`：备用验证码输入。
5. `PASSWORD`：扫码或手机号登录触发的两步验证。
6. `READY`：短暂成功状态，由控制器随即关闭。

二维码由本地库根据 Telethon 返回的 `tg://login?token=...` URL 生成图像，不调用第三方二维码服务，不把令牌发送到 Telegram 之外的网络端点。二维码只在内存中呈现，不写入磁盘。

## 4. 组件与边界

### 4.1 Telegram 网关

在现有网关协议增加三个行为：

- `begin_qr_login()`：确保客户端已连接，调用 Telethon `qr_login()`，返回 URL 和过期时间的不可变值对象。
- `wait_qr_login()`：等待当前令牌被手机端导入；成功返回 `READY`，遇到 `SessionPasswordNeededError` 返回 `PASSWORD_REQUIRED`。
- `refresh_qr_login()`：调用当前 `QRLogin.recreate()` 并返回新 URL/过期时间。

网关持有当前 QRLogin 对象，但不向 UI 暴露 Telethon 类型。没有活动令牌时等待或刷新必须返回可安全展示的领域错误。

### 4.2 控制器

控制器负责登录状态机和任务生命周期：

- 凭据保存成功后启动 QR 流程。
- 已保存凭据时，`show_login()` 默认启动 QR 流程。
- 用一个受控异步任务等待扫码，用另一个短周期 UI 计时器更新倒计时；不并发等待多个令牌。
- 扫码成功和手机号成功共用现有 `_finish_login()`，确保会话保存与账号徽章行为一致。
- 关闭、刷新、切换方式和应用退出都走统一取消函数。
- 用户修改 API/代理配置时，先断开旧客户端并取消旧 QR，再以新配置创建客户端。

### 4.3 登录对话框

UI 只负责展示和发送用户意图，不直接调用 Telethon。新增信号：

- `qr_refresh_requested`
- `phone_fallback_requested`
- `credentials_edit_requested`
- `login_cancelled`

新增展示接口：

- `show_qr(url, expires_at)`
- `update_qr_countdown(seconds)`
- `show_qr_status(text)`

二维码图像生成封装为独立纯函数/小组件，便于测试尺寸、空白边界、无磁盘写入和内容一致性。

## 5. 数据、安全与隐私

- API ID 继续写入 `data/config/settings.json`；API Hash 和代理密码继续通过 DPAPI 写入 `data/config/secrets.dat`。
- StringSession 登录成功后继续通过 DPAPI 保存。
- 两步验证密码、手机号验证码、QR URL 和 QR token 永不持久化。
- 日志只记录状态和错误类别，不记录敏感值或完整异常消息。
- 所有新增缓存、临时状态和测试输出仍位于项目/应用目录，不向 C 盘持久写入业务数据。
- 应用仅授权当前 Telegram 账号正常可访问的内容，不改变现有权限边界。

## 6. 错误处理

- API 凭据无效：返回凭据页并显示“API 凭据无效”。
- 代理或网络不可用：停留在当前页，允许修改设置或重试。
- QR 过期：自动刷新；连续刷新失败后停止循环并显示手动重试。
- QR 被拒绝或令牌无效：丢弃当前令牌并允许生成新二维码。
- 需要两步验证：切换到 `PASSWORD`；错误密码只显示安全中文提示。
- 用户取消：取消任务并断开未授权客户端，不保存不完整会话。
- 已经由其他路径完成授权：视为成功并进入统一完成流程。

## 7. 测试策略

所有生产改动按测试驱动方式实现，至少覆盖：

- 网关创建、刷新、等待 QR 登录，成功和 2FA 分支。
- 无活动 QR、过期、网络失败、取消和重复刷新。
- 控制器首次配置后进入扫码、已有凭据直接扫码、切换手机号备用、关闭时取消任务。
- 扫码和手机号两条路径都通过同一完成函数保存加密 StringSession。
- 对话框默认页、按钮、状态、倒计时、二维码替换和敏感字段掩码。
- 二维码生成不访问网络、不写文件，编码内容与 Telethon URL 一致。
- 日志与产物秘密扫描不包含 QR token、API Hash、验证码、2FA 密码或会话。
- 打包主程序包含二维码生成依赖，便携/安装模式 `--self-test`、GUI 冒烟和在线更新回归通过。

## 9. 验收条件

- 首次使用只需配置一次个人 API ID/API Hash，随后默认显示二维码。
- Telegram App 扫码确认后，程序自动完成登录并保存加密会话。
- QR 过期可自动/手动刷新，不产生重叠等待任务。
- 开启 2FA 的账号能在扫码后完成密码验证。

- 关闭或切换登录方式后无残留 QR 等待协程。
- 所有应用数据仍保存在应用目录，正式产物不包含用户凭据。
