# TelegramDownloader v0.11.0 下载资源控制设计

## 1. 背景与目标

v0.10.0 已具备链接/相册/批量扫描、账号内容搜索、自动订阅、断点续传、任务工作台、文件完整性修复、图形化诊断和双源签名更新。真实代码审计显示，现有 `DownloadScheduler` 的文件并发信号量由全部任务共享，不会按任务数无限放大；但所有任务会同时创建下载协程并竞争文件槽位，用户无法预知任务先后、持久化调整优先级或限制总下载速度。设置中的并发修改也只会保存到磁盘，当前连接中的调度器不会立即采用新值。

v0.11.0 的目标是把“任务队列”变成真实、可预测、可控制的调度队列：

- 同一时刻只执行一个下载任务；任务内部继续使用 1–5 个共享文件槽位。
- 普通任务按持久化优先级、创建时间和任务 ID 稳定排序，默认遵循先进先出。
- 用户可以把一个等待任务提升到队首；正在下载的任务不被隐式中断。
- 用户可以设置总下载速度上限，并让并发与限速在当前连接中即时生效。
- 界面明确显示活动任务、等待数量、队列位置、并发和限速状态。
- 暂停、继续、失败重试、完整性修复、订阅任务、重启恢复和关闭程序继续保持安全、无重复和可续传。
- 所有业务数据、临时文件和发布验证数据仍只位于项目或应用目录，不新增 C 盘持久数据。

## 2. 方案比较

### 方案 A：下载资源控制与可预测队列（采用）

在现有调度器内增加任务级准入队列，并复用已有文件级并发。在任务表增加一个兼容迁移字段保存用户优先级；下载器共享一个异步带宽限制器。改动集中在下载主链路，能直接缓解多个任务同时争抢、队列状态不透明和网络占用不可控的问题。

### 方案 B：跨群组全局搜索

一次搜索多个已加入群组有较高内容发现价值，但需要多会话分页、公平调度、全局结果持久化和更复杂的 FloodWait 管理。它不会改善已有任务的执行可预测性，本轮不采用。

### 方案 C：多账号切换

多账号需要将会话、内容目录、搜索历史、任务去重、订阅和密钥全部增加账号边界，并设计旧数据归属迁移。范围和数据风险明显高于本轮资源控制，本轮不采用。

## 3. 调度语义

### 3.1 两级调度

保留现有 `DownloadScheduler` 作为唯一调度边界，但明确分为两级：

1. 任务级：同一时刻最多一个活动任务，其余请求进入等待队列。
2. 文件级：活动任务内部最多同时下载 `concurrency` 个媒体项。

这样可保持单任务多文件吞吐，同时避免多个大任务的媒体协程互相穿插。任务完成、暂停或形成部分失败后，调度器立即释放任务槽位并启动下一项。

`run_task()` 与 `run_items()` 保持“等待本次操作结束才返回”的现有异步合同，现有调用方和测试不需要理解内部队列。重复提交同一任务时共享当前操作，不创建第二次下载。完整性修复的 `run_items()` 也是显式队列操作；如果同一任务已有活动操作，它先等待该操作完成，再只处理仍符合条件的选中项。

### 3.2 顺序与持久化

`tasks` 表新增：

```text
queue_priority INTEGER NOT NULL DEFAULT 0
```

等待任务按以下键排序：

```text
queue_priority DESC, created_at ASC, id ASC
```

旧数据库迁移后全部任务优先级为 0，因此按创建时间先进先出，不改变任务、媒体、去重或文件记录。点击“优先下载”时，仓库只允许未归档的 `queued` 任务获得当前最大优先级加一；调度器同步重排内存等待队列。任务真正开始后清零其优先级，防止以后继续或修复时意外长期插队。

应用重启恢复时使用仓库的同一排序键提交等待任务，因此尚未开始的“优先下载”意图可以跨重启保留。正在下载、扫描或等待重试的任务仍先由现有恢复逻辑安全回到 `queued`，媒体 `.part` 文件不变。

### 3.3 暂停、关闭与竞态

- 暂停活动任务：设置暂停标志；当前媒体在下一个分块边界落盘并变为暂停，任务释放活动槽位。
- 暂停等待任务：从内存队列移除并完成对应等待操作，数据库变为 `paused`，不会短暂开始下载。
- 继续任务：数据库先变为 `queued`，再按当前普通优先级进入队列。
- 优先下载与调度同时发生时：如果任务仍在等待则重排；如果已开始则报告“已经开始下载”，不重复运行。
- 关闭程序：停止接受新请求，移除等待项并安全完成等待调用；活动任务沿用 30 秒优雅暂停与取消兜底。

## 4. 并发与总带宽限制

### 4.1 可调整文件并发

用内部可调整异步许可器替代固定 `asyncio.Semaphore`。许可器保持 1–5 范围和 FIFO 等待：

- 增大并发时立即唤醒足够的等待媒体。
- 减小并发时不取消正在传输的媒体；只阻止新媒体进入，直到活动数低于新上限。
- 等待协程取消时必须从等待队列移除，不能泄漏许可。

### 4.2 共享带宽限制器

`AppSettings` 新增 `speed_limit_kib: int = 0`。`0` 表示不限速；正式界面提供不限速、256 KiB/s、512 KiB/s、1 MiB/s、2 MiB/s、5 MiB/s、10 MiB/s、20 MiB/s 和 50 MiB/s 预设，设置加载同时兼容未来的 0–1,048,576 KiB/s 安全整数值。

所有 `MediaDownloader` 调用共享同一个异步带宽限制器。每个 Telegram 分块写入前按字节数预约时间片；预约使用单调时钟和串行锁，使多个媒体的合计长期速率不超过设置值。不限速路径不等待。限速只控制媒体正文下载，不延迟登录、群组同步、搜索、缩略图或更新检查。

修改并发或限速时，控制器在原子保存设置后调用调度器的运行时配置方法：新并发立即用于后续许可，新限速立即用于后续分块。已经预约的单个分块最多在原等待时间后采用新速率，因此界面提示“已应用，当前分块可能需数秒切换”。API 或代理变更继续在下次连接时生效。

限速等待中如收到取消会自然响应 `CancelledError`；暂停在当前分块预约结束后处理。正式预设的最低速度把常见 512 KiB 分块的最长暂停反馈控制在约 2 秒，仍低于关闭宽限。

## 5. 用户界面与交互

### 5.1 设置

“并发下载”改名为“文件并发”，帮助文案说明它作用于当前活动任务；新增“总下载限速”下拉框。保存后的状态消息区分：

- 下载资源设置已即时应用；
- API/代理设置已保存，将在下次连接时生效。

### 5.2 任务工作台

操作栏新增“优先下载”，仅在恰好选中一个未归档、状态为 `queued` 的任务时可用。点击后不弹出确认框，立即重排并显示结果反馈。

任务表不增加宽列；等待任务的状态文本显示为“等待中 · 第 N 位”。活动任务仍显示“下载中”。右侧实时概览新增一行调度摘要：

```text
调度：1 个下载中 · 3 个等待 · 文件并发 3 · 不限速
```

无活动任务时显示“调度：空闲”。队列位置来自调度器内存快照；刚启动、尚未提交到内存的极短窗口只显示“等待中”，不会伪造位置。

控制器只允许活动任务的 `_run_and_refresh` 循环触发周期数据库刷新；等待任务仅在入队、重排、暂停和结束时刷新，避免 N 个等待任务产生 N 份相同查询。

## 6. 组件边界

- `settings.py`：新增限速字段验证并保持缺失字段向后兼容。
- `bandwidth.py`：提供可独立测试的异步带宽限制器和可调整并发许可器，不依赖 Qt 或 Telegram。
- `downloader.py`：写分块前调用共享限速器；暂停、磁盘空间、哈希和原子改名流程保持不变。
- `scheduler.py`：拥有任务等待队列、单活动任务、队列重排、位置快照、运行时资源配置和安全关闭。
- `repository.py` / `domain.py`：兼容迁移、优先级读写、稳定恢复排序；不改媒体唯一键。
- `controller.py`：统一提交队列、优先操作、调度摘要、活动任务刷新和即时设置应用。
- `ui/main.py` / `ui/models.py` / `ui/settings.py`：按钮、状态位置、摘要和限速预设。

不创建 Windows 服务、计划任务、注册表自启动、用户目录缓存或任何新的远端服务。

## 7. 错误处理与隐私

- 所有任务 ID、群组信息、链接、原始文件名和绝对路径继续不进入用户可导出的诊断摘要。
- 优先操作遇到任务消失、状态变化或归档时作为安全跳过，状态栏显示通用反馈。
- 带宽/并发设置损坏时沿用 `SettingsError`，不自动覆盖用户文件。
- 调度器内部异常沿用控制器 `_safe_error` 脱敏；等待队列本身不写独立日志或数据库正文。
- 新数据库字段不含 Telegram 内容或凭据。

## 8. 兼容与数据无损边界

- v0.10.0 设置缺少 `speed_limit_kib` 时自动使用 0，不改写文件直到用户保存。
- v0.10.0 任务数据库只增加带默认值的列；迁移前后所有既有列值、行数和媒体唯一键必须相同。
- DPAPI 凭据、Telegram 会话、账号目录数据库、缩略图、诊断包、下载文件、`.part` 和更新备份不参与转换。
- 直启版升级只复制 v0.10.0 的 `data` 与 `downloads` 到新的 v0.11.0 运行目录；原 v0.10.0 目录只读保留。
- 安装升级/卸载沿用既有非 C 盘安装和保留用户数据合同。

## 9. 测试与验收

### 9.1 自动化

- 设置：旧 JSON 默认值、限速合法/非法值、原子往返、界面所有预设。
- 带宽：不限速零等待、单流速率、多流合计速率、单调时钟、取消和运行时切换。
- 并发许可：上限、增大、减小、FIFO、取消不泄漏。
- 仓库：旧表迁移、优先级条件更新、重复提升、稳定恢复排序、任务开始清零、旧数据列哈希不变。
- 调度器：一次只运行一个任务、FIFO、持久优先顺序、运行时插队、重复提交、等待暂停、活动暂停、继续、失败重试、`run_items`、关闭与文件并发。
- 下载器：限速器在落盘前按每个分块调用，暂停/失败仍保留正确 `.part` 和进度。
- 界面/控制器：按钮资格、队列位置文案、摘要、优先反馈、活动任务单一刷新、设置即时应用。
- 端到端：链接、账号搜索和订阅各创建任务，验证统一队列、去重、优先、暂停/重启续传与限速。
- 包装：版本、隐式导入、README/发行说明、自检、更新与 ZIP 隐私合同。

### 9.2 三轮自检

1. 开发轮：全量 Pytest、Ruff、核心队列/限速压力与竞态测试。
2. 集成轮：干净工作树重跑全量测试，结构化代码审查，修复后再次全量验证。
3. 发布轮：冻结程序、便携包、安装包、签名更新、ZIP 隐私扫描和远端资产回读。

### 9.3 真人化 QA

使用 v0.10.0 项目内真实数据的隔离副本，不输出凭据、群名、任务标题或文件名：

- 启动复用会话，不出现重复二维码；群组同步与搜索仍可操作。
- 连续创建至少三个可控下载任务，确认只有一个活动任务并显示正确位置。
- 把末尾任务设为优先，确认它在当前任务结束后最先执行。
- 下载中切换 256 KiB/s、2 MiB/s 和不限速，观察总速度和界面反馈；不要求瞬时分块无抖动。
- 暂停活动任务、继续、关闭并重启，确认 `.part` 续传且无重复媒体。
- 选中已完成媒体执行校验/修复，确认修复操作也通过统一队列。
- 对原始 v0.10.0 目录与隔离副本的设置、凭据、两座数据库、下载文件和行数做前后哈希/计数比对。
- 验证进程写入路径、临时目录、安装路径和卸载残留均在 D/F 盘指定根目录内。

## 11. 本轮不包含

- 抢占或强制暂停正在下载的任务。
- 每任务独立限速、定时下载、夜间规则或系统托盘后台服务。
- 拖拽排序、复杂多级优先级或删除任务/文件。
- 跨群组全局搜索、多账号、自动加入群组。
- 对 Telegram 搜索、缩略图、群组同步或在线更新限速。
