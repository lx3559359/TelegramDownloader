# TG 快取搜索结果响应性能优化设计

## 背景

TG 快取 v0.18.1 已具备渐进搜索、搜索 generation 隔离、批量文件写入、动作去重和增量 Qt 模型更新。现有搜索结果上限为 10,000 条，但当前 `SearchResultTableModel.apply_results()` 对每个目标结果线性查找当前行，并在多处重复复制完整列表。该实现会随结果数量接近平方增长。

2026-08-24 在当前开发机使用真实模型类与合成 `SearchResult` 的基线结果如下：

| 结果数 | 首次应用 | 仅修改一行 |
| ---: | ---: | ---: |
| 100 | 5.96 ms | 13.46 ms |
| 500 | 15.74 ms | 10.49 ms |
| 1,000 | 61.93 ms | 55.92 ms |
| 2,000 | 227.31 ms | 207.91 ms |

搜索路径还存在三类主线程等待：

1. 搜索页提交、历史读取和结果重载直接执行同步 SQLite 调用。
2. 单项勾选会同步写数据库、重新读取全部结果并重置模型；全选和反选会逐条开启数据库操作。
3. 加入下载队列的预检、去重、任务提交和结果回写在 Qt/asyncio 事件循环中同步执行。

本轮按现有 10,000 条产品上限优化搜索结果显示、历史切换、勾选和加入队列响应，目标版本为 v0.18.2。

## 已确认的产品取舍

- 采用“线性差异模型 + SQLite 后台化”方案。
- 保留现有表格、渐进搜索、滚动浏览、全选、反选、缩略图和加入下载队列流程。
- 优先保证主线程响应、稳定 ID 状态保留和数据库一致性，不用模型全量重置掩盖常规增量更新问题。
- 按 10,000 条结果设计和验收，不把上限降为 2,000，也不改为仅显示 200–500 条的虚拟分页。

## 目标与非目标

### 目标

- 搜索结果模型的快照比较和索引维护保持 O(n)，不再出现嵌套全表查找。
- 10,000 条结果的首次装载、稳定快照更新、历史切换和选择操作不产生明显的多秒卡顿。
- SQLite 搜索提交、历史读取、选择写入和入队预检不在 Qt 主线程执行。
- 保留顶部可见结果、当前行、勾选状态和已加载缩略图。
- 单项快速连续勾选只持久化每个结果的最终状态；全选和反选使用一个数据库事务。
- 搜索、历史和选择的延迟返回受搜索 ID、generation 和操作代次保护。

### 非目标

- 不修改 Telegram 搜索 API、FloodWait 策略、搜索结果含义或结果上限。
- 不提高搜索、相册、缩略图或下载并发。
- 不修改数据库 schema、下载目录、命名模板、任务格式或在线更新协议。
- 不重写整个 Controller、Qt Model/View 或 SQLite 仓库架构。
- 不承诺网络、代理或 Telegram 服务端响应时间；本轮只消除本地可控阻塞。

## 1. 结果模型

### 1.1 稳定 ID 索引

`SearchResultTableModel` 继续以 `SearchResult` 为公开数据对象，内部增加：

- 按显示顺序保存的结果序列。
- `result_id -> row` 索引。
- 按结果 ID 保存的缩略图映射。

每次结构变化完成后只重建一次行索引。输入快照必须保证结果 ID 唯一；重复 ID 视为调用方错误，测试中直接失败，生产界面显示安全错误并保留旧模型。

### 1.2 O(n) 快照应用

`apply_results()` 一次构建当前 ID 集合、目标 ID 集合和目标行映射，然后按以下路径处理：

1. **相同 ID 与相同顺序：** 一次替换内部结果序列，只为真实变化的连续行范围发出 `dataChanged`。
2. **有删除：** 从后向前删除连续范围；如果删除范围过度碎片化，则执行一次受控重建，而不是逐行移动。
3. **有新增：** 把所有新 ID 作为一个连续尾部块加入，再用一次布局变更切换到目标顺序；不会逐个在 Python 列表中间插入。
4. **仅重排：** 使用一次 layout change，并按稳定 ID 重映射 persistent index。
5. **病理快照：** 当结构差异超过固定碎片阈值时允许一次 O(n) 受控重建；页面负责恢复可见锚点和当前结果。常规搜索批次、单行更新和选择操作不得走该路径。

整个算法不调用嵌套 `next()`、`list.index()` 或逐次完整 `tuple()` 复制。缩略图只移除目标快照中已不存在的 ID。

### 1.3 可见位置和状态恢复

`ContentBrowserPage` 在结构更新前记录：

- 视口顶部可见结果 ID。
- 当前结果 ID。
- 水平滚动位置。

更新后通过模型行索引恢复对应位置。勾选状态来自目标 `SearchResult`，缩略图来自 ID 映射；二者不依赖旧行号。账号切换或搜索 generation 切换可以清除旧锚点，但同一搜索内的渐进批次不得跳回表格顶部。

## 2. 渐进更新合并

页面维护一个只接收不可变 `SearchResultBatch` 的更新缓冲：

- Service 交给页面的每个 batch 都表示当前搜索与 generation 的累计展示快照，而不是只能单独解释的增量片段；下一页直接命中必须与此前稳定结果合并后再发送。
- 空模型收到当前 generation 的第一批结果时立即应用，不增加人为首屏等待。
- 同一搜索与 generation 的后续非稳定批次只保留最新快照，并在不超过约 33 ms 的窗口内合并，避免多个网络回调触发连续全表重绘。
- 稳定批次立即替换待处理批次并刷新，使“加入下载队列”及时恢复可用。
- 搜索 ID 或 generation 改变时丢弃旧缓冲；页面关闭或账号切换时取消定时器。
- 模型应用期间不主动请求缩略图；应用完成后只安排一次可见行缩略图扫描。

缓冲只合并界面快照，不延迟数据库提交、搜索进度、取消或 Telegram 请求。

## 3. SQLite 与本地计算线程边界

### 3.1 后台调用原则

以下工作通过 `asyncio.to_thread()` 或项目现有等价执行边界运行：

- `begin_search`、`get_session`、`list_sessions`、`list_results` 和 `commit_search_page`。
- 搜索结果选择写入、全选、反选和失败后的数据库真值重载。
- 入队预检、重复项查询、任务持久化和已入队结果回写。

工作线程只接收不可变参数，只返回 dataclass、元组、计数或安全错误。工作线程不得访问 QWidget、Qt Model、asyncio Task、当前页面或状态栏。

`CatalogRepository` 每次操作继续打开短连接；增加仓库级线程锁保护同一实例的事务边界。线程中的 SQLite 操作即使调用方取消也允许自然结束，锁保证后续仓库操作不会与其交叉写入。

### 3.2 搜索提交

Telegram 网络请求和相册扩展继续在 asyncio 事件循环执行。取得一页不可变结果后，以下本地工作作为一个后台阶段执行：

- 查询稳定结果和已入队媒体键。
- 计算本页稳定结果。
- 在一个 SQLite 事务中写结果、更新游标和状态并返回最新快照。

后台阶段返回时，Controller 再检查当前搜索 ID、generation 和 task 身份。失配结果只记录非敏感计数，不更新页面。

### 3.3 历史切换

历史行点击改为异步的 `replace_latest` 动作：

1. 页面保留当前结果并显示“正在加载历史结果…”。
2. 工作线程一次读取目标 session 和结果快照。
3. 只有最新历史请求且账号未改变时才切换模型。
4. 读取失败时保留原页面并显示安全错误。

直接信号处理器不再同步调用 `list_sessions()`、`list_results()` 或 `set_results()`。

## 4. 选择与入队

### 4.1 单项勾选

模型收到鼠标或键盘选择后立即更新该行并发出选择意图。页面在约 50 ms 的短窗口内按结果 ID 合并意图，同一 ID 只保留最终布尔值。Controller 维护单个选择写入循环：运行中的事务完成后继续处理期间积累的新意图，不丢弃其他行的变化。

仓库新增单事务批量选择接口。成功时不重新读取全部结果、不重置模型；失败时异步读取当前搜索的数据库真值，并且只在搜索 ID、generation 和选择操作代次仍匹配时校正页面。

### 4.2 全选与反选

全选与反选分别使用一个受搜索 ID 和 generation 限制的 SQL 更新：

- 全选只影响 `available=1 AND queued=0` 的当前 generation 结果。
- 反选只翻转同一可选择集合。
- 已入队或不可用结果始终保持未选择。

界面先用一次 O(n) 模型操作即时显示目标状态，数据库后台事务成功后保持；失败则按数据库快照校正。操作期间新的单项选择进入后续选择批次，不会被较早事务覆盖。

### 4.3 加入下载队列

点击后同步设置局部忙碌状态，然后依次后台执行预检和提交：

1. 读取已选结果并完成不可用、已入队和重复统计。
2. 回到主线程显示现有确认对话框。
3. 用户确认后在后台创建一个任务并批量标记成功入队结果。
4. 返回主线程应用结果补丁并刷新任务摘要。

任务仓库与内容目录不实现伪造的跨数据库事务。任务成功提交后，以 `committed.accepted_keys` 为事实来源批量更新内容目录；如果目录回写失败，则保留已创建且可恢复的下载任务，立即通过任务仓库中的媒体键重新校正结果状态。再次点击时沿用现有媒体键去重，不能创建第二个重复任务。

取消确认不写任务。预检失败不清空用户选择；目录回写失败不回滚已经安全提交的任务，也不把未被任务仓库接受的结果标记为已入队。

## 5. 并发、取消与错误处理

- 搜索、加载更多和历史切换采用“最新请求生效”；旧任务的线程结果不能恢复已取消页面。
- 搜索结果尚未稳定时继续禁止加入下载队列，确保相册完整性和去重语义不变。
- 选择写入按搜索 ID 和 generation 隔离；账号切换会清空待处理选择并等待或忽略旧事务结果。
- 线程工作不可被强制终止；取消只停止等待和后续 UI 应用，仓库锁保证正在提交的短事务完整结束。
- 数据库失败、重复 ID、非法 generation 和入队失败统一映射为现有安全错误摘要。
- 日志只记录固定动作类型、搜索范围类型、结果数量、模型插入/删除/更新数量、事务次数和耗时；不得记录关键词、聊天标题、peer、消息 ID、摘要、文件名、路径或 Telegram 响应正文。

## 6. 性能观测与验收

### 6.1 模型基准

新增独立、可重复的模型基准脚本或测试辅助器，使用固定合成结果分别测量 100、500、1,000、2,000 和 10,000 行。验收要求：

- 10,000 行首次装载和单行变化在当前开发机的多次运行中位数各不超过约 100 ms。
- 10,000 行耗时不得呈现相对 2,000 行约 25 倍的平方增长；目标增长不超过 8 倍。
- 单行变化只发出覆盖变化行的 `dataChanged`，不得发出 model reset。
- 常规追加、删除和稳定重排使用有界数量的结构信号。

绝对时间用于本机发布证据，不作为依赖共享 CI 硬件速度的脆弱单元测试断言；自动化测试断言操作次数、信号范围和线性数据访问合同。

### 6.2 事件循环与数据库合同

- 注入 300 ms 仓库延迟时，Qt/asyncio 心跳仍持续推进，搜索状态、取消和其他页面按钮可以响应。
- 单项勾选不调用全量 `list_results()`，连续点击同一行只保存最终状态。
- 全选和反选分别只创建一个事务，不逐结果开启连接。
- 历史连续点击只显示最后一次请求，旧线程返回被丢弃。
- 搜索提交、取消和失败继续满足 generation 隔离及稳定结果恢复合同。
- 入队预检与提交期间主线程心跳继续推进，并且只创建一个任务。

### 6.3 状态保持与回归

- 10,000 条结构更新后顶部可见结果、当前行、勾选和缩略图仍按稳定 ID 保持。
- 搜索第一批直接命中仍先于相册扩展显示；稳定前仍禁止入队。
- FloodWait、离线重连、账号切换、历史删除、缩略图缓存和任务刷新行为保持兼容。
- 数据库 schema 版本、设置、任务、订阅、下载文件、DPAPI 凭据和在线更新协议保持不变。

## 7. 三轮自检

完成实现后执行三轮独立自检：

1. 完整 pytest、Ruff、模型基准和事件循环心跳测试。
2. 便携包全新构建、打包冒烟，以及 10,000 条合成搜索页面交互检查。
3. 安装器构建与安装冒烟，并在 Windows GUI 中检查搜索首屏、历史快速切换、单项连续勾选、全选/反选、滚动锚点和入队确认。

三轮都必须记录命令、通过数量、基准中位数、产物大小和 SHA-256。任一轮失败都不得标记完成或发布。
