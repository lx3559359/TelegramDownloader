# Telegram 下载、搜索与全应用交互性能优化设计

## 背景

当前版本已具备下载队列、断点续传、账号范围搜索、专辑补全、缩略图缓存、自动订阅、健康诊断和统一异步动作反馈。相关功能测试稳定，但关键热路径仍会把磁盘、SQLite 或模型重置工作放在 Qt 事件循环中，形成三类可见延迟：

1. 下载器接收每个 Telegram 分块后都调用文件 `flush`，同步文件操作与哈希工作会占用事件循环，降低吞吐并影响界面刷新。
2. 搜索必须等待远端整页结果、所有专辑展开、去重和持久化全部结束后才显示结果，首屏等待偏长。
3. 任务、内容、订阅、诊断、登录和设置中的部分操作会同步查询数据库、处理文件或整表重置 Qt 模型，按钮虽然有反馈框架，但主线程仍可能卡顿。

本设计采用分层增量优化，不改变现有 Controller → Service/Gateway → SQLite/Qt 总体架构，也不通过无界并发换取短期速度。

## 已确认的产品取舍

- 优化目标采用均衡模式：同时改善下载吞吐、搜索首屏和全应用交互响应。
- 下载允许批量落盘。异常崩溃时最多重新下载最后一个小批次，暂停、取消、正常关闭和完成仍强制同步磁盘。
- 搜索允许渐进显示。直接命中先出现，专辑补全、去重和缩略图随后完成，短时间内允许少量行增加或调整。
- 工具交互覆盖整个应用，包括任务、内容、订阅、诊断、登录和设置。

## 目标与非目标

### 目标

- 点击耗时操作后，在同一个 Qt/asyncio 事件循环内显示忙碌或进行中状态。
- UI 热路径不执行可能超过约 100 毫秒的同步数据库、文件、哈希、压缩或网络工作。
- 下载以批量写入替代逐分块刷新，同时保持断点续传、暂停和完整性校验语义。
- Telegram 返回直接命中后立即呈现首批结果，不等待所有专辑和缩略图。
- 批量任务操作只进行一次持久化批次、一次聚合读取和一次界面更新。
- 保持 Telegram 请求并发有界，继续尊重 FloodWait，不绕过服务端限制。

### 非目标

- 不重写为独立下载进程或新的事件总线架构。
- 不提高现有文件并发上限 5，也不引入无界专辑、缩略图或搜索并发。
- 不改变下载文件命名、目录、安全边界、账号会话保存或更新签名机制。
- 不承诺不受网络、Telegram 服务端、代理、杀毒软件或磁盘硬件影响的固定绝对速度。

## 1. 下载管线

### 1.1 `BufferedPartWriter`

在下载器内部引入职责单一的 `BufferedPartWriter`。它只负责把一个媒体项的字节安全追加到对应 `.part` 文件，并报告已经完成系统写入的字节数。

- 网络分块先进入应用级 `bytearray`。
- 缓冲累计约 1 MiB，或自上次批量写入经过 0.5 秒时，提交一个批次。
- 实际文件写入和该批次的 SHA-256 更新通过后台线程执行，调用方始终按顺序等待，单个媒体项不会出现并发写文件或并发更新摘要。
- 暂停、取消、磁盘检查前需要精确偏移时先写完缓冲。
- 暂停、取消、正常关闭和完成时执行 `flush` 与 `fsync`；普通中间批次不执行 `fsync`。
- 完成时先确认预期大小和摘要，再关闭流并用 `os.replace` 原子提升为最终文件。

每个写入器分别维护：

- `received_bytes`：已经从 Telegram 接收并通过限速器的字节。
- `persisted_bytes`：已经提交给文件写入操作的字节，也是数据库和界面进度的依据。
- `durable_bytes`：最近一次 `fsync` 确认的字节，仅用于恢复和测试，不作为常规高频界面字段。

异常进程退出后，恢复逻辑仍以 `.part` 的实际文件大小为准，并在开始续传时纠正数据库进度。这样不会信任可能领先于文件的旧数据库值。

### 1.2 暂停、取消和空间检查

- 带宽等待仍按现有约 50 毫秒节奏检查暂停，避免降低控制响应。
- 暂停在当前短批写入结束后生效，写完缓冲并 `fsync`，随后持久化精确偏移和 `PAUSED` 状态。
- `CancelledError` 走与暂停相同的落盘收尾，但继续向上传播，不能转换成普通下载失败。
- 磁盘空间仍按 16 MiB 下载增量复查；复查前不要求每块 `flush`，只使用已接收量计算剩余需求。
- 写入失败、空间不足或大小异常时保留 `.part`，不创建最终文件。

### 1.3 进度与资源控制

- 下载数据库进度最多每 0.5 秒写入一次，并且只写 `persisted_bytes`。
- 控制器任务汇总仍最多每 0.5 秒刷新，但后续采用增量模型更新。
- 保留现有单活动任务、多文件并发、实时 1–5 并发调节和共享总限速。
- 不通过提高 Telethon 请求并发解决磁盘瓶颈。

## 2. 渐进搜索与缩略图

### 2.1 搜索阶段

搜索过程明确分成四个阶段：

1. **远端扫描**：Gateway 返回经过日期、类型和媒体有效性筛选的直接命中，并继续报告已扫描/已匹配计数。
2. **临时呈现**：Service 把直接命中转换成当前搜索代次的临时结果批次，Controller 立即增量显示。
3. **专辑补全**：按 `(peer_ref, grouped_id)` 合并触发项，最多并发 4 组展开；每个完整专辑在单个事务中写入。
4. **稳定提交**：完成去重、数量上限、已入队检查、最终排序和会话游标更新，再撤销或替换临时行。

单会话搜索和全账号搜索复用相同阶段。全账号搜索继续使用 `messages.SearchGlobalRequest` 及其 `next_rate`、来源 peer 和消息 ID 游标，不更改已验证的分页契约。

### 2.2 临时结果安全

- 临时结果只属于当前账号、搜索 ID 和 generation，不作为可下载记录。
- 搜索处于远端扫描、临时呈现或专辑补全阶段时，加入下载队列操作保持禁用。
- 新搜索取消旧搜索后，旧 generation 的进度、临时结果、专辑结果和缩略图回调全部丢弃。
- 取消或失败时重新加载已提交结果，清除临时行，并把会话标记为不完整。
- 非专辑结果可在稳定提交阶段直接保留；专辑必须整体持久化，不能把仅有触发项的残缺专辑留作可选择结果。

### 2.3 SQLite 往返

新增面向一页搜索结果的事务接口，在一个连接和事务中完成：

- 校验账号、搜索 ID 和 generation。
- 读取本代次已存在媒体键。
- 写入完整非专辑结果和已补全专辑。
- 更新结果计数、游标、完成状态、错误摘要和时间。
- 返回最新会话、总结果数和本次变更集。

这样替代当前每页多次 `list_results`、`get_session`、`save_search_page` 和 `finish_search` 往返。数据库仍保持短连接模式，不在本轮引入常驻共享连接。

### 2.4 结果模型和缩略图

- 搜索结果模型增加按稳定结果 ID/媒体键应用插入、更新和删除变更集的接口。
- 稳定排序为消息时间倒序，再按来源、消息 ID 和媒体 ID 排序。
- 增量更新尽量保留滚动位置、选择状态和已加载缩略图；只有账号或搜索代次整体切换时允许模型重置。
- 缩略图仍只请求可见行，网络并发保持最多 4。
- 相同缩略图键的并发请求共享同一个 in-flight task。
- 确认无缩略图或发生局部错误后进入短时失败冷却；滚动或重复绘制不会立即重发相同请求。
- 搜索、预览和表格共享缓存文件与 in-flight 请求。

## 3. 全应用交互响应

### 3.1 动作策略

扩展现有 `AsyncActionBridge`，为动作声明以下策略：

- `deduplicate`：刷新、诊断、登录、重连、缓存清理等同键动作只保留一个运行实例。
- `replace_latest`：搜索、页面内容加载和依赖最新表单快照的动作由新请求取消旧请求。
- `batch`：暂停、继续、重试、归档、恢复、校验等选择操作先去重 ID，再作为单个批次执行。

动作的 `started` hook 在后台任务创建前同步执行，因此按钮文字、禁用状态或进度提示会在同一事件循环内出现。`finished` hook 在成功、失败和取消路径统一恢复界面。

### 3.2 主线程边界

逐一审计所有 Qt 信号处理器，并遵循以下边界：

- Qt 控件、模型信号和对话框只在主线程访问。
- SQLite 聚合查询和批量事务、文件哈希、缓存扫描/删除、诊断压缩导出、可能阻塞的系统调用通过 `asyncio.to_thread` 执行。
- Scheduler 的 asyncio 状态变更继续在事件循环中执行；其持久化部分改用仓库批量接口，不能在工作线程直接操作 asyncio 对象。
- 页面切换先显示内存或 SQLite 缓存，再启动 Telegram 刷新。
- 本地筛选和简单 O(1) 控件状态更新保留在主线程，避免为极小操作增加线程调度开销。

### 3.3 批量任务与模型更新

- 批量任务命令使用一个仓库事务检查并更新所有目标，不再逐 ID 打开连接。
- 命令完成后只查询一次 `list_task_snapshots` 和一次队列快照。
- 任务模型按任务 ID 应用差异，只更新变化行；筛选、当前任务、媒体选择和滚动位置保持稳定。
- 下载进度刷新由所有并发下载共享一个节流入口，避免多个任务同时触发重复全量读取。

### 3.4 覆盖范围

响应优化覆盖：

- 下载任务：暂停、继续、失败重试、优先级、归档、恢复、文件校验和修复。
- 内容页：激活、群组刷新、搜索、加载更多、选择、加入队列、缩略图和预览。
- 自动订阅：创建、更新、启停、立即运行、只读测试和删除。
- 健康诊断：运行、取消、导出和打开目录。
- 登录与连接：凭据提交、二维码刷新、手机回退、取消和重连。
- 设置：代理测试、保存和缩略图缓存清理。

打开文件、打开目录、纯页面导航和内存筛选等本地即时动作不强制进入异步桥，但不得执行额外扫描或网络请求。

## 4. 错误、取消与关闭

- 后台工作只向 UI 返回不可变结果或变更集，不能从工作线程直接操作 Qt。
- Worker 异常回到动作桥后映射为现有安全错误摘要；`finally` 恢复局部界面状态。
- 搜索中的专辑或缩略图局部失败不终止已取得的其他结果。
- FloodWait 保留明确等待秒数提示，不进行无界重试。
- 关闭时停止接收新动作，取消可取消的搜索/网络工作，并在现有关闭宽限内等待短文件批次完成。
- 不强制杀死仍在执行文件系统调用的线程，也不删除可能可恢复的 `.part`。
- 日志仅记录固定动作键、结果类型、耗时和非敏感计数；不得记录账号、peer、消息、关键词、链接、文件名、绝对路径、凭据或 Telegram 响应正文。

## 5. 性能观测与验收

### 5.1 确定性自动化测试

- 使用 8 MiB 数据和 64 KiB 网络分块验证下载不再产生 128 次文件刷新，且最终大小和 SHA-256 正确。
- 用可注入时钟、批量阈值和文件写入器验证 1 MiB/0.5 秒触发条件，不依赖脆弱的机器绝对时间。
- 注入慢文件写入时运行事件循环心跳，证明磁盘工作不阻塞 UI 协程。
- 验证暂停、取消、磁盘不足、大小不符和异常关闭后的 `.part`、数据库偏移及最终文件语义。
- 使用受控专辑阻塞器证明直接结果先于专辑完成呈现，最终专辑完整、去重且排序稳定。
- 验证搜索 generation 隔离、取消清理、失败保留以及全账号游标不回退。
- 验证相同缩略图并发只调用一次 Gateway，失败冷却期间不重复请求。
- 验证动作桥的即时 `started`、去重、替换、批量、取消和异常恢复。
- 验证大任务列表只更新变化行，批量命令只执行一次界面刷新和聚合读取。

### 5.2 回归与人工验收

- 运行完整 pytest 和 Ruff。
- 对下载、搜索、页面切换、任务操作、订阅、诊断、登录和设置执行 Windows GUI 冒烟检查。
- 在相同模拟流和配置下比较优化前后吞吐、文件写入/刷新次数、SQLite 往返次数和模型重置次数；以相对改善为准，不使用与硬件绑定的绝对速度门槛。
- 确认现有下载并发、共享限速、断点续传、任务队列、搜索历史、会话恢复、目录守卫和隐私测试全部保持通过。
